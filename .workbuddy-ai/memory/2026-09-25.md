# THEOLOGICUS — 2026-09-25

## v119 — le demarrage Windows etait lent : 10,7 s de sondage de ports

Signalement : *« pour la version windows, je vois que ca prend un peu de temps
avant d'ouvrir alors que cetait pas le cas avant »*. Le « avant » etait exact.

### Cause — mesuree, pas deduite

`trouver_instance_existante()` (v117, commit `c002857`) sondait **les 16 ports de
la plage AVANT de demarrer un serveur**, et le faisait **deux fois par port** : la
sonde d'identite `/__theologicus_ping`, puis le contenu de `THEOLOGICUS.html`
(cense couvrir une instance d'une ancienne version du exe).

Or, sur cette machine, un port de la plage **qui n'est ni ouvert ni refuse (aucun
RST) fait expirer le timeout entier** : 0,4 s. Mesure :

```
16 ports x (0,4 s ping + 0,4 s html) = 10 669 ms
```

L'ancien `pick_port` faisait **deux `bind` au maximum** (0,0 ms) : il ne payait
rien. La regression est donc bien nee avec la v117, et `git log -- app.py` le
confirme (seul `c002857` a touche ce code entre `ac2eb36` et aujourd'hui).

### Quand la lenteur frappait

| Chemin | Cout v117 |
|---|---|
| THEOLOGICUS tourne deja sur 8765 (instance a nous) | **26 ms** (arret immediat) |
| 8765 occupe par un AUTRE programme | **10 619 ms** |
| Lancement neuf, 8765 libre | **10 627 ms** |

Le cas lent est donc **tout lancement ou 8765 n'est pas deja a nous** — ce qui est
la situation courante : apres une mise a jour, l'ancien processus n'a pas encore
rendu le port, et la v117 avait deplace le projet Theo de 8765 vers 8770-8772.

### Correctif — « ne sonder que ce qui peut repondre »

`resoudre_port(ports)` remplace les deux fonctions :

1. **Le `bind` d'abord.** Un bind reussi est une preuve **instantanee** que le
   port est libre : on s'arrete la, sans aucune requete.
2. **Sonde uniquement sur un port occupe.** Donc un serveur repond : le cout est
   de quelques millisecondes, jamais un timeout.
3. **Une seule sonde** : le test HTML redondant est supprime. Il ne servait que
   la transition depuis une version anterieure a la v117, desormais revolue.
4. `PING_TIMEOUT` 0,4 → **0,25 s**. La sonde est locale ; elle n'a pas besoin
   d'une marge prevue pour le reseau.

Resultat mesure : **11 504 ms → 0,1 ms** (gain mesure x176 000 sur le chemin neuf),
**23,5 ms** quand une instance est deja en ecoute. Le port choisi et le verdict
d'instance restent **identiques** : la stabilite d'origine introduite en v117 —
la raison d'etre du bloc — n'est pas entamee.

### Banc

`_v119/verify_demarrage.py` — **10/10** : demarrage sous 300 ms, **aucune sonde
sur un port libre** (espion sur `_est_notre_serveur`), ancienne strategie
chronometree pour comparaison, **meme port et meme verdict** que l'ancienne,
choix du **premier** port libre (deterministe), stabilite sur deux appels, plage
saturee → `(None, False)` sans exception, et un port vide n'est pas reconnu comme
nous (sinon on « reutiliserait » le serveur d'un autre programme).

### Lecon durable

**Un bind repond a la question « ce port est-il libre ? » en 0 ms ; une requete
HTTP repond a « qui ecoute ? » en 0,4 s s'il n'y a personne.** Sonder avant de
binder, c'est payer le prix du cas le plus frequent (personne) pour un resultat
que le bind donnait gratuitement. Et **deux sondes ne valent pas mieux qu'une**
quand la seconde n'existe que pour une transition de version : elle coute a
chaque lancement, pour toujours, un service rendu une seule fois.

## Étude de Beacon (Asymptote Labs) — pour l'outillage d'agent, pas l'application

Demande : *« analyse ce dépôt https://github.com/Asymptote-Labs/agent-beacon et tu
me dis comment implémenter dans mon Theologicus »*, puis, après clarification :
*« implémente cela dans ton système plutôt alors »*.

Analyse complète dans **`artifacts/BEACON_ANALYSE.md`**. Ce qu'il faut retenir :

**Ce qu'est Beacon** : une couche de mémoire pour agents de **codage**. Il capte
les sessions (hooks `beacon-hooks` + OTLP local + poll), normalise en événements
OpenTelemetry, écrit une **JSONL locale** (`~/.beacon/endpoint/logs/runtime.jsonl`,
rotation 10 MiB / 5 archives), en tire des leçons **relues et approuvées** par un
humain, réutilisables via **MCP** et **Agent Skills**. MIT, local-first, aucune
dépendance hébergée. Pour l'application THEOLOGICUS elle-même : **rien à voir**.

**Trois points d'intégration** : serveur MCP `beacon mcp serve` (7 outils :
`search_activity`, `summarize_activity`, `get_activity_event`,
`list_activity_filters`, `search_memory`, `get_memory`, `get_memory_context`) ;
trois skills `beacon-memory-recall|distill|promote` ; CLI `beacon memory …`
(candidat → `approve` → `skills install`).

**La contrainte decisive** : WorkBuddy **n'est pas un harnais supporté**. Recherche
exhaustive du dépôt entier : **aucune occurrence de « WorkBuddy » ni
« CodeBuddy »**, ni dans le code, ni dans les docs, ni dans les manifestes. La
capture passe par un **fichier de hooks propre à chaque harnais**
(`~/.claude/settings.json`, `~/.cursor/hooks.json`…) que WorkBuddy n'expose pas.
`beacon endpoint hooks install` ne peut donc pas le brancher → le JSONL resterait
**vide**. **Installer Beacon sur cette machine serait un tuyau sans eau.**

Je ne l'ai **pas** installé, pour trois raisons assumées : (1) le skill officiel
dit explicitement *« Do not install it yourself »* — je ne passe pas outre une
consigne de sécurité d'un tiers sans accord ; (2) ce serait inerte (§ ci-dessus) ;
(3) le nom `beacon` est déjà pris par le projet Théo sur cette machine.

**Ce qui a été intégré à la place** (le vrai livrable), dans
`~/.workbuddy-ai/MEMORY.md` — créé à cette occasion, valable tous projets :

1. **Test de non-duplication avant création d'un skill.** Promouvoir : les
   procédures et conventions valables pour BEAUCOUP de tâches, et un motif de
   débogage pour une panne qui REVIENT. Laisser en mémoire : les pièges ponctuels
   liés à un seul fichier/incident, et **tout ce qui duplique déjà les notes long
   terme ou la doc du projet** (corriger la doc, pas créer un skill). Raison :
   chaque skill s'ajoute à ce que l'agent considère à **chaque** tâche.
2. **Approuvé ≠ brut** : un journal daté est une trace non vérifiée ; une note
   longue durée ou un skill est de la connaissance **vérifiée sur pièce**.
3. **Requêtes par termes ET-és** : deux ou trois termes distinctifs, jamais une
   phrase entière ; retirer des termes si le premier essai est vide.

**Audit de contrôle effectué** : mes quatre skills `theologicus-*` (31 280 / 20 259
/ 20 716 / 17 861 octets) **ne dupliquent pas** `MEMORY.md` (5 174 o) — le
chevauchement mesuré est marginal (`sync_html` 2 vs 1, `paths:` 4 vs 1, signature
5 vs 2) et les notes longues renvoient **vers** les skills au lieu de les
recopier. L'architecture existante passe donc le test. Point de vigilance
signalé à l'utilisateur : `theologicus-apk-build` est très volumineux (579
lignes), à surveiller.

**Ce qui reste ouvert** : si WorkBuddy devient un harnais supporté, brancher
`beacon endpoint hooks install`, vérifier que le JSONL se remplit, puis déclarer
le serveur MCP dans `~/.workbuddy-ai/mcp.json`. Les trois skills
`beacon-memory-*` seraient alors repris tels quels.

**Ce qui reste transposable** (et ne demande aucune ligne d'OpenMontage) :
manifests déclaratifs — `THEO_CORPORA` joue déjà ce rôle, un YAML embarqué
supprimerait la classe de bug « dossier absent des trois listes » ; portes
d'approbation par étape — déjà le motif du mode narrateur / validation avant TTS
coûteux ; auto-revue bloquante avant livraison — `check_syntax.js` +
`sync_html.py` + `verify_*.js` le font déjà, la leçon est de la rendre
**systématique**. Même conclusion que pour Beacon : **le principe se reprend, le
code ne se reprend pas**.

**Aucun fichier de l'application n'a été touché** : étude seule, rien à
synchroniser, rien à committer côté `THEOLOGICUS.html`.

## Étude de MoneyPrinterTurbo 1.3.7 (portatif Windows) — le premier AVEC une API

Chemin local : `C:\Users\toshr\Desktop\MoneyPrinterTurbo-Portable-Windows-1.3.7`
(2,4 Go). Amont `harry0703/MoneyPrinterTurbo`, commit `ad5496f1` du **2026-09-24**
(projet **actif**), licence **MIT**.

Analyse complète dans **`artifacts/MONEYPRINTERTURBO_ANALYSE.md`**.

**Rupture avec les trois études précédentes** : **il y a une vraie API HTTP**.
`main.py` lance **uvicorn** (`app.asgi:app`, défaut **8080**, `/docs` Swagger).
`app/router.py` monte les contrôleurs V1, préfixe **`/api/v1`**. Endpoints réels :
`GET /ping` ; `POST /api/v1/videos` (génère), `/subtitle`, `/audio` ;
`GET|DELETE /api/v1/tasks[/{id}]` ; `POST /api/v1/scripts`, `/terms`,
`/social-metadata` ; `GET|POST /api/v1/musics`, `/video_materials` ;
`GET /api/v1/stream|download/{path}`. `VideoParams` est un **modèle Pydantic** →
surface contractuelle et documentée. `app/asgi.py` fait de la sécurité sérieuse
(clé API optionnelle, 403 sur Origin non fiable, repli des origines par
`_normalize_allowed_origin()`, CORS, Private Network Access, file de tâches,
option Redis) — **code de qualité production**.

**Verdict : pas un « modèle extra » non plus, mais pour une raison inverse.**
Le blocage n'est plus « rien à appeler », c'est **la nature de l'objet** :

1. **Ce n'est pas un modèle, c'est un pipeline.** `/api/v1/videos` ne rend pas du
   texte mais un **MP4** au bout d'un job asynchrone long (rushes Pexels, TTS,
   `faster-whisper`, `moviepy`, ffmpeg). Un modèle rend une réponse de
   conversation ; ici l'unité de travail est un **job**.
2. **Port instable — le piège exact de la v117.** `start.bat` et `webui.bat`
   choisissent le port en boucle **8501→8599** (premier libre). Et
   `listen_host = "0.0.0.0"` dans le `config.toml` local : écoute **toutes les
   interfaces**.
3. **2,4 Go** (`lib/python` 848 Mo dont 684 Mo de `site-packages`, `lib/git`
   376 Mo, `lib/ffmpeg` 82 Mo, ffmpeg **7.0**), et **deux services** : WebUI
   Streamlit (8501+, `start.bat`) ou API (8080, `api.bat`).
4. **Clés tierces obligatoires** : rushes Pexels/Pixabay, et un LLM pour le script
   (`config.toml` local : `llm_provider = "moonshot"`, clé vide).

**Pendant positif — le meilleur candidat des quatre si l'objectif est la vidéo.**
THEOLOGICUS sait déjà parler à un service local : c'est le motif **Supertonic**
(`tools/start_supertonic.py`, routes `/supertonic/…` dans `proxy_server.py`) et
**LibreTranslate**. Intégration raisonnable si demandée : **ne rien embarquer**
(l'utilisateur lance MPT lui-même), déclarer un connecteur dans `proxy_server.py`
(sonde `/ping` en lecture seule + relais `POST /api/v1/videos` puis polling
`GET /api/v1/tasks/{id}`), **journaliser le port trouvé** (leçon v117), et
**présenter le résultat comme un livrable MP4**, pas comme un message.

**Grille de lecture des quatre études** : agent-beacon → pas de harnais supporté ;
OpenMontage → aucun client LLM ; stable-diffusion → aucun serveur **et** figé en
2022 ; MoneyPrinterTurbo → **une API complète**, mais un **outil**, pas un modèle.
**Toujours vérifier (a) l'existence d'une surface appelable, (b) la date du dernier
commit, (c) la nature de l'unité de travail (réponse vs job).**

## v120 — STUDIO VIDÉO : connecteur MoneyPrinterTurbo, IMPLÉMENTÉ

Demande : *« je veux un modal dans le header Studio Vidéo, en cliquant dessus j'ai
toutes les fonctions de MoneyPrinterTurbo, avec les configurations etc. »*

### Ce qui a été livré

Bouton **🎬 STUDIO VIDÉO** dans le header (+ entrée burger mobile + deux commandes
de palette `Studio v` / `Studio g`). Modal `#studio-modal` au patron
`modal-overlay`/`modal-box` existant, exposant les fonctions réelles : sujet,
script, **format** (9:16/16:9/1:1), durée de plan, nombre de vidéos, enchaînement,
langue, source de rushes, **voix**, vitesse, volume, musique, **sous-titres**
(activation, position, taille, couleurs), plus bouton *enregistrer les réglages*.

Le mode de fabrication retenu — et c'est le point : **on n'intègre pas LEUR
interface, on intègre LEUR API derrière la nôtre.** Leur WebUI (`webui/Main.py`,
**8 262 lignes**) n'est pas un front sur l'API : il **importe directement
`app.services`** (`task as tm`, `bgm_service`, `state as sm`) et tourne sous
Streamlit dans le même processus. Aucun `api/v1` ni `requests.post` vers l'API
dedans. Il est donc **non extraytable**. L'API `/api/v1`, elle, est parfaitement
appelable.

Connecteur dans `proxy_server.py` (voisin de Supertonic/LibreTranslate) :
`GET /mpt/status|tasks|config|download/<path>` ;
`POST /mpt/start|submit|poll|delete|config`. Relais **obligatoire** : la page est
en `127.0.0.1:8765`, appeler `127.0.0.1:8080` serait cross-origin (MPT n'ouvre
CORS que sur `CORS_ALLOWED_ORIGINS` explicite). Garde anti-traversée sur le
téléchargement (`[A-Za-z0-9_\-]{1,64}`), formulaire dans
`%LOCALAPPDATA%/THEOLOGICUS/theologicus_studio.json` (écriture atomique).

### Deux défauts trouvés en testant contre le service RÉEL

1. **`http_proxy` piège la boucle locale.** `HTTP_PROXY`/`http_proxy` sont définis
   dans l'environnement de cette machine et **urllib les honore pour
   `127.0.0.1`**. Le proxy ne peut pas joindre la boucle locale et rend **502 Bad
   Gateway** — message qui *ressemble* à « le service a répondu 502 » alors que
   MPT **n'a jamais reçu la requête**. C'est ce qui m'a d'abord fait conclure à
   tort « service absent » alors qu'il tournait. Correctif :
   `_boucle_locale()` → `build_opener(ProxyHandler({}))`.
   **Preuve retenue** : `ProxyHandler` est **absent** de `opener.handlers` quand
   `proxies={}` — cette **absence** est le test, pas une table vide.
2. **FastAPI `-> str` rend `"pong"` AVEC guillemets** (corps JSON). La sonde
   n'acceptait que `pong` nu. Elle accepte désormais **les deux** : ce qui compte
   est l'identité du service, pas un détail d'encodage.

Pièges de banc rencontrés, tous dus au service réel qui tournait :
`8080` répondait pour de bon → les assertions « service absent » échouaient **à
tort** ; le faux service du banc restait en écoute → `mpt_lancer` répondait
légitimement « déjà lancé ». **Correctif : ports privés au banc (8790+), et
arrêt du faux service avant de tester les refus.** 43/43 → **50/50**.

### Preuve de bout en bout, contre le service vivant

`mpt_status()` → `{running: true, port: 8080}` (journalisé). `GET /api/v1/tasks`
→ `total: 1`. Un **vrai envoi** `POST /api/v1/videos` → `task_id`
`5545362b-…`, puis `poll` → `state:-1, progress:5, failed_stage:"script",
error:"moonshot: api_key is not set…"`. L'échec est **attendu** (aucune clé
configurée) et l'UI **remonte désormais `failed_stage` et `error` tels quels** :
« échec » seul obligerait l'utilisateur à fouiller MPT pour une cause qui est ici.

### Leçon durable

**Un banc qui n'isole pas ses ports du vrai service produit de faux échecs ; un
relais qui ne désarme pas le proxy système produit un faux diagnostic.** Les deux
ont été vécus dans la même heure. Et : **immerger l'API d'un tiers derrière SA
propre interface est la seule intégration honnête quand leur front est couplé à
leur processus** (Streamlit + imports directs).

### Git — piège opérationnel

`git add -A` sur ce dépôt (99 entrées + HTML de 1,5 Mo) **dépasse le délai** et
rend **SIGTERM**, laissant un **`.git/index.lock` orphelin** qui fait échouer les
appels suivants (« Another git process seems to be running »). Solution :
**stager les fichiers explicitement** (`git add THEOLOGICUS.html proxy_server.py …`)
puis `git commit -F`, et **supprimer `.git/index.lock`** s'il est orphelin.
Commit `236cd5a` poussé.

### Le défaut le plus grave, trouvé APRÈS le build : `sync_html.py` bénissait une installation périmée

`sync_html.py` acceptait **n'importe quelle** cible portant un tampon de version
comme « déployée », **sans jamais comparer la fraîcheur**. Le tampon prouve
seulement que le fichier **sort d'un build**, pas qu'il est **récent**.

Mesure : `_inst_v102/THEOLOGICUS.html` datait de **05:53** alors que la source
venait d'être corrigée à **15:20**. Conséquence : **le bouton 🎬 STUDIO VIDÉO
était ABSENT de l'installation réellement lancée** pendant que le script
affichait « OK » et « **0 copie(s) mise à jour** ». C'est le pire cas de la règle
« un correctif non synchronisé est invisible » : l'outil **cachait** activement le
problème au lieu de le signaler.

Correctif : exiger en plus que **la cible soit au moins aussi récente que la
source**, sinon recopier. Preuve immédiate — la règle resserrée a attrapé
`_inst_v102` **et** `dist`, les deux sont maintenant identiques à la source
(md5 `2d869ce23fce` sur les quatre copies). Commit `4ed625f` poussé.

## v121 — parité avec l'interface MoneyPrinterTurbo

Demande : « je veux toutes les fonctionnalités que tu vois ici car c'est le même
déjà présent dans l'interface de MoneyTurbo » (capture du WebUI MPT jointe).
Le formulaire passait de 12 à ~50 champs, en **quatre panneaux** : sujet et

### Deux défaillances réelles, toutes deux invisibles

**1. `$(id)` sans dièse — de nouveau, et sous une forme nouvelle.**
`$` = `document.querySelector`, il exige le `#`. Neuf appels passaient
l'identifiant **en variable** (`$(id)`, `$(idS)`, `$(idPick)`, `$(bouton)`),
donc le `#` ne pouvait pas figurer dans le littéral. `querySelector("studio-voice")`
cherche une **BALISE** `<studio-voice>` → `null` → `if (e)` saute. **Zéro
exception.** Trois symptômes distincts, tous imputables au service à tort :
- les curseurs bougeaient, leur étiquette restait figée ;
- la pipette et le champ texte divergeaient ;
- les listes (voix, polices, musiques) restaient vides.
Correctif : **`_SEL = document.getElementById`**, point d'accès unique dans le
bloc studio. **Leçon de méthode :** un audit qui ne cherche que
`$("litteral")` rate tous les `$(variable)`. Auditer **tout** `$(x)` où `x`
n'est pas un littéral commençant par `#`.

**2. `mpt_requete` n'utilisait pas `_boucle_locale()`.**
`http_proxy` est défini dans l'environnement et **urllib l'honore aussi pour
127.0.0.1** → le proxy ne joint pas la boucle locale → **502**. `_mpt_probe`
désarmait déjà ce piège, **pas** `mpt_requete`. Conséquence : `/mpt/status`
rendait `running:true` pendant que **chaque** requête échouait. Un défaut qui
accuse le service voisin. **Règle : toute sortie HTTP vers la boucle locale passe
par `_boucle_locale()`.**

### Autres correctifs

- `bgm_type` → **`bgm_name`**, `text_color` → **`text_fore_color`**. MPT ignore
  les anciens noms : la musique ne jouait pas, le texte restait noir.
- `mpt_fonts` cherchait `resource/fonts` à la **racine** du portatif, alors que
  l'application vit dans le **sous-dossier `MoneyPrinterTurbo/`**. Résolution par
  `_mpt_racines()` (sous-dossier d'abord, racine ensuite), **partagée** avec
  `mpt_voices`. Mesuré : **331 voix** dont **15 françaises**, **9 polices**,
  **29 musiques**.
- Français en **premier groupe** du sélecteur de voix ; `STHeitiMedium.ttc`
  présélectionnée — ce sont les défauts du service.
