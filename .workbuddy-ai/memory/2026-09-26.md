### Pourquoi un iframe et pas un copier-coller

Le document redéfinit `body`, `:root` et `*` dans sa feuille de style : collé
dans THEOLOGICUS il **repeindrait toute l'application**. Il déclare aussi 104
fonctions globales, dont `escapeHtml` et `toast` — déjà présents chez nous.
L'iframe est de **même origine** (servi par le relais) : il isole CSS et JS,
partage le stockage local, et permet les appels `/proxy/…`.

### Deux défauts du relais trouvés en chemin

1. **`/proxy/` n'existait qu'en `do_POST`.** Un `GET /proxy/…` recevait un 404
   de la distribution de fichiers **avant** tout appel au fournisseur. La
   vérification de clé (un `GET /models`) aurait affiché « clé invalide » pour
   une clé parfaite. Branché aussi dans `do_GET`.
2. **La méthode était forcée à POST** (`conn.request('POST', …)`) → 405 sur
   tout le reste. On transmet maintenant `self.command`, et tous les en-têtes
   entrants sauf `Host`/longueur/hop-by-hop (une liste fermée perd
   silencieusement l'en-tête qui manque).

Troisième piège : le relais est **mono-thread**, il ne peut pas se relayer
lui-même (502 systématique). Le banc vise donc un serveur témoin sur un autre
port qui renvoie la méthode reçue.

### Le compagnon doit être propagé

`ai-video.html` est un **deuxième fichier** : `tools/sync_html.py` propage
désormais les `COMPAGNONS` vers `mobile/www`, `dist` et `_inst_v102`. Oublié,
l'iframe serait **vide et muet** — invisible en développement.
Au passage, bug latent corrigé dans `sync_html.py` : `getmtime(source)` au
lieu de `getmtime(SOURCE)`, un `NameError` avalé par le `except` qui faisait
recopier les cibles estampillées à chaque synchronisation.

L'utilisateur voyait le cadre vide même après le correctif précédent. Cause
racine : **relais périmé sur 8765**. `THEOLOGICUS.bat` faisait `start
proxy_server.py` sans libérer le port ; un relais démarré avant
`ai-video.html` gardait 8765, le nouveau `start` échouait à s'attacher, et le
navigateur frappait le relais périmé → 404 → cadre vide. Rouvrir l'app ne

- `THEOLOGICUS.html` : détection d'échec au **titre** du document
  (`indexOf("AI VIDEO")`), et auto-guérison via `srcdoc` (fetch du fichier et
  injection ; ai-video.html est autonome, zéro ressource relative) ; sinon
  message de repli clair au lieu d'un cadre muet.

Vérifié `verify_aivideo_ui.js` 18/18 sur relais frais. Le relais sert déjà
`no-store`/`no-cache` → pas de cache navigateur à craindre.

Leçon à retenir : tout fichier compagnon servi par le relais doit être
propage (sync_html COMPAGNONS), détectable au titre, et le lanceur doit tuer
tout relais résiduel sur le port stable.

## v126h — « Erreur réseau » sur Vérifier : pas un bug d'iframe ni de relais

Symptôme : l'utilisateur saisit ses clés (persistées en v126g) mais « Vérifier »
dit « Erreur réseau », alors que les clés sont neuves.

Repro headless (Chromium-1234) sur 3 chemins de l'iframe, relais mocké PUIS
relais réel vers l'API Agnes réelle :
- A-normal (`ai-video.html` servi) : fetch `/proxy/...` → 200 mock → valide.
- B-srcdoc (fallback `about:srcdoc`, exe sans compagnon) : idem — PAS de bug
  de résolution d'URL relative dans un iframe srcdoc.
- C-file:// (ouverture directe, `_VIA_RELAIS=false`) : fetch direct → 401 réel
  → « Clé invalide » (l'API renvoie `Access-Control-Allow-Origin: *`).
- Serveur style-exe (ThreadingHTTPServer 127.0.0.1) + relai réel → 401 réel
  « Clé invalide ». Le chemin relais→API est sain.

Conclusion : le code courant renvoie TOUJOURS un statut lisible (valide /
invalide / HTTP n), jamais « Erreur réseau », quand le relais et/ou l'API
sont joignables. « Erreur réseau » (fetch REJETÉ, pas un statut HTTP) ne
survient que si le relais ne peut PAS sortir — p.ex. derrière un proxy
d'entreprise : proxy_server utilise `http.client` SANS proxy système, alors
que WebView2 utilise la config OS. Le relais échoue (502/404/rejet), le
navigateur, lui, sortirait.

Correctif (`ai-video.html`) : helper `_verifCle(apiBaseRelais, apiBaseDirect,
key, applyUI)` — si le relais est mort (fetch rejeté, 502, ou 404 HTML d'un
relais obsolète), repli sur un fetch DIRECT vers l'URL nue (`_VIA_RELAIS` et
CORS `*` le permettent). De plus, on ne fait plus `res.json()` aveuglément
(un 404 HTML le faisait lever → « Erreur réseau » à tort) : on lit le texte
et on ne parse que si Content-Type JSON (ou `{` en tête). Les messages sont
précisés (« Erreur réseau — relais local injoignable », « HTTP n — relais ? »).

Vérifié : `verify_aivideo_keys.js` 8/8 (régression), `verify_aivideo_network.js`
3/3 (normal + srcdoc + file://), `verify_aivideo_real_relay.js` OK (401 réel).

NOTA banc : `frameLocator().evaluate(b=>b.click())` nécessaire — le
`click()` Playwright était avalé (hit-test/overlay du HUD). Pour ouvrir le
modal : `addInitScript` pose `localStorage['theologicus_wizard_skipped']='1'`
puis `document.getElementById('open-aivideo-modal').click()` via `evaluate`.

## v126j — 429 : respecter Retry-After et reprendre automatiquement

Pendant une génération vidéo avec image, l'API peut renvoyer HTTP 429
(rate limit). L'ancien `apiFetch` attendait une séquence codée en dur
(15, 30, 45...) et relançait encore une requête après le dernier essai.

Correctif : lire `Retry-After` (secondes ou date HTTP), afficher « Limite API
— reprise automatique », attendre le délai fournisseur, puis reprendre. Au
dernier essai, retourner la dernière réponse 429 au lieu de lancer une
requête immédiate supplémentaire. Le test `verify_aivideo_429.js` prouve
429 + Retry-After: 1 s → nouvelle tentative → 200 en 4/4. Régressions :
keys 8/8, fallback 6/6, UI 18/18.
