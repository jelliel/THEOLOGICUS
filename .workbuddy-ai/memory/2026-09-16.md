## v45 — l'encadrement ne se lance plus à la sélection

Demande : « le bubble pour l'encadrage doit se lancer SEULEMENT au double-tap,
pas quand je sélectionne un mot / une phrase ».

### Cause trouvée par élimination
`openInsertMenuAt()` n'a que **trois** appelants :

| Ligne | Déclencheur | S'ouvre à la sélection ? |
|---|---|---|
| 18453 | action 📐 dans la bulle (clic délibéré) | non |
| 18593 | double-tap (v42) | non |
| **19056** | **`contextmenu` sur `.message-content`** | **OUI** |

Or **sur Android, l'appui long émet `contextmenu`** — et l'appui long est
précisément le geste pour sélectionner un mot ou une phrase. Sélectionner
ouvrait donc le menu d'encadrement à la place de la bulle « Add to chat ».

Correctif : sur tactile, la branche `.message-content` du `contextmenu` est
court-circuitée (`__THEO_TOUCH_UI()` → `mc = null`). Les branches surlignage
(`.atc-mark`, `.atc-hl`) et figure (`.atc-figbox`) sont **conservées** :
l'appui long est leur seul moyen d'accès sur mobile. Le clic droit souris
garde l'encadrement (aucune régression desktop).

### Ambiguïté tranchée avec l'utilisateur
Sur Android, **double-taper un mot = le sélectionner** : « double-tap » et
« sélectionner un mot » sont le même geste physique. Les séparer exigerait
d'imposer « sélectionner d'abord, puis double-taper ». Question posée →
**l'utilisateur choisit de garder le double-tap direct (v42)**. Le double-tap
sur un mot non sélectionné encadre donc toujours ; c'est voulu.

### Leçon
Face à « X se lance quand je fais A, je veux X seulement sur B », ne pas
deviner : **lister les appelants de la fonction** et éliminer ceux qui ne
peuvent pas correspondre au geste décrit. La cause devient évidente en une
recherche, là où deux hypothèses plausibles s'affrontaient.

`93d832…` inchangée. Commit `6f9941f` poussé → `main` =
`6f9941f6952af3234d0eeef0cb1c0a4ee1b4e230`. CI #20 en cours.

## v46 — l'encadrement restait affiché (retour utilisateur)

Retour : « appui long sur un mot → j'ai la bulle **en plus de** l'encadrement ».
v45 n'avait donc pas suffi. Deux causes, la première étant la vraie :

### 1. Le menu d'encadrement ne se fermait qu'au `mousedown`
`document.addEventListener('mousedown', ...)` fermait `#atc-insert-menu`. Or
**un appui long sur Android n'émet pas de `mousedown`** (il émet `contextmenu`).
L'utilisateur avait ouvert l'encadrement par double-tap juste avant : le menu
était resté à l'écran, et l'appui long suivant affichait la bulle **par-dessus
un menu jamais fermé**. D'où « la bulle **en plus de** l'encadrement ».
→ Ajout d'un fermeture sur `touchstart` hors du menu (v46).

### 2. Fausse paire de taps
Le détecteur de double-tap comptait **tout** `touchend`. Un appui long dure
~500 ms et le glissement d'une poignée de sélection produit un **second**
`touchend` : les deux pouvaient former une paire valide (< 350 ms, < 40 px).
→ v46 n'accepte que des taps **francs** : pressions < 250 ms **et** sans
`touchmove` de plus de 12 px. Sinon la paire est oubliée (`_tapT = 0`).

### Test des gestes — `_diag_v46.js`
Séquences `Touch`/`TouchEvent` synthétiques (Chrome headless, émulation tactile) :

| Geste | Résultat attendu | Obtenu |
|---|---|---|
| appui long 600 ms | bulle seule | ✅ bulle seule |
| double-tap franc (2 × 80 ms) | encadrement | ✅ encadrement |
| glissement 40 px + tap | bulle seule | ✅ bulle seule |
| menu ouvert + touche ailleurs | menu fermé | ✅ `block` → `none` |

Piège du test : viser `elementFromPoint(200, 400)` tombait **dans** le menu
(ouvert à cet endroit) → la fermeture ne se déclenchait pas, à juste titre.
Il faut choisir un point **hors** de `getBoundingClientRect()` du menu.

### Leçon
Un retour du type « j'ai A **en plus de** B » ne décrit pas forcément deux
déclencheurs concurrents : c'est souvent **B qui n'a jamais été fermé**.
Vérifier les fermetures avant de chercher un second déclencheur.

## v47 — le commentaire d'annotation était inaccessible sur mobile

Signalé : « après une annotation, je clique sur le passage annoté et rien ne
s'affiche ».

**C'était une régression v41.** Le commentaire s'ouvrait au `mouseover`. Comme
un tap émet `mouseover`, l'infobulle s'ouvrait au lieu de laisser sélectionner
le texte — j'avais donc désactivé le survol au doigt… **sans le remplacer**. Le
commentaire est resté injoignable sur mobile pendant 6 versions.

Correctif, trois parties :
1. **`click` sur `.atc-hl` → `showTipFor`**, avec 400 ms de délai au doigt
   pour qu'un double-tap puisse l'annuler.
2. **Fermeture au `touchstart` hors de l'infobulle** : elle se fermait au
   `mouseleave`, événement inexistant au doigt → elle serait restée à l'écran.
3. **Suppression de 700 ms** (`_tapPairAt`) : le `click` arrive **après** le
   `touchend`, donc le double-tap détecté était contourné par le clic qui
   reprogrammait l'infobulle. Sans ce drapeau le test 2 échouait.

Test `_diag_v47.js` — 4 cas, tous verts : tap → commentaire affiché ;
double-tap → rien ; touche ailleurs → fermé ; survol souris → inchangé.

### Piège du test
`applyHighlights` n'est **pas** global (elle vit dans l'IIFE ATC). Utiliser
`window.__applyHighlights`, exposée ligne 11230. `renderMessages` et `state` le
sont. Pour créer une annotation de test : `state.messages = [{...,
annotations:[{id,text,a,loading:false}]}]` puis `renderMessages()` +
`window.__applyHighlights()`.

### Leçon récurrente
Désactiver un déclencheur au doigt **sans le remplacer** = supprimer la
fonction. À chaque garde `__THEO_TOUCH_UI`, se demander quel geste prend le
relais.

### Audit de toutes les gardes tactiles (fait, une seule victime)
`__THEO_TOUCH_UI` a 6 usages : définition (18268), traduction masquée v44
(18517 — volontaire, serveur injoignable), double-tap v42 (18598), appui long
v45 (19089 — remplacé par le double-tap), survol infobulle v41 (19763 —
**victime**, remplacée en v47), tap infobulle v47 (19783). Aucune autre
fonction morte.

Les infobulles de référence (bible 17995 / quran 18116 / tafsir 18227) sont
aussi en `mouseover`, **mais** `.bible-ref` est un `<a href target="_blank">` :
le tap ouvre le lien, la fonction n'est donc pas perdue. À ne pas « corriger ».

## LibreTranslate depuis le téléphone — lanceur corrigé

Symptôme : « en voulant traduire un mot, ça me demande le serveur
`py tools\start_libretranslate.py` », et au lancement :
`No module named libretranslate.__main__; 'libretranslate' is a package and
cannot be directly executed`.

**Cause** : le script lançait `python -m libretranslate`. **LibreTranslate
1.9.x n'a pas de `__main__.py`** — vérifié : le dossier du paquet contient
`main.py` mais aucun `__main__.py`. Le point d'entrée officiel est
`libretranslate.main:main` (déclaré dans `entry_points.txt`, exposé aussi par
le script `libretranslate.exe` dans `AppData\Roaming\Python\Python314\Scripts`).

**Correctif** (`tools/start_libretranslate.py`, fonction `lt_command`) :
```bash
python -c "from libretranslate.main import main; main()" --host 0.0.0.0 --port 5000
```
Le passage par `-c` est indépendant du PATH et du dossier Scripts — donc
fiable que l'installation soit globale, `--user` ou dans un venv.

**Vérifié** : `/languages` répond ; traduction en→fr réelle →
« Dieu a tant aimé le monde » ; préflight CORS depuis l'origine
`https://localhost` → 200 avec `Access-Control-Allow-Origin: *` (indispensable,
l'app est cross-origin) ; `usesCleartextTraffic="true"` déjà présent au
manifest v58.

**Reste à faire par l'utilisateur** : règle de pare-feu (nécessite
l'élévation — `netsh advfirewall firewall add rule …` échoue sans admin) et
saisie de l'URL dans le popup ⚙️ de l'app.

**Pourquoi la découverte auto ne suffit pas** : le code essaie l'URL
enregistrée, `localhost:5000`, la passerelle (`NetBridgePlugin`, présent) puis
`.1`/`.2` du sous-réseau du téléphone. Le PC est en **`.8`** → jamais essayé.
Saisie manuelle obligatoire (mémorisée dans localStorage).

**À signaler** : l'installation `pip install --user` a **rétrogradé**
`beautifulsoup4` en 4.9.3 et `rich` en 12.6.0, cassant `crawl4ai`, `gtts` et
`typer` (avertissement pip explicite). Un venv dédié serait plus propre.

Commit `d7dd309` poussé → run CI #41 **success** → release `apk-v1.0.39`.
L'alignement de signature tient : SHA-256 `93d832…` (DN complet
`CN=THEOLOGICUS, OU=Mobile, O=THEOLOGICUS, C=FR`), identique au build local.

## v63 — lanceur LibreTranslate : fausse IP + faux avertissement

L'utilisateur : « pourquoi j'ai cette erreur » en collant la sortie de
`py tools\start_libretranslate.py`.

### 1. Ce n'etait PAS une erreur
`RequestsDependencyWarning: urllib3 (2.7.0) or chardet (7.6.0)/
charset_normalizer (3.5.0) doesn't match a supported version!`
→ **cosmetique**. Le serveur demarrait (« Running on http://0.0.0.0:5000 »)
et traduisait. Cause : `requests` 2.31.0 (laisse par `pip install --user
libretranslate`) face a urllib3 2.7.0 / chardet 7.6.0 trop recents.

**Pourquoi le filtre enfant ne marchait pas** (piege) : j'avais bien ajoute
`warnings.filterwarnings(...)` dans la commande `-c` de l'enfant, mais
l'avertissement partait quand meme. Test direct du filtre : il marchait.
→ La vraie source etait le **processus parent** : `have_module()` faisait un
`__import__("libretranslate")`, qui importe `requests`, AVANT tout filtre.
→ `have_module()` utilise maintenant `importlib.util.find_spec` (aucun import,
aucun effet de bord, bien plus rapide) + filtre pose aussi dans le parent.

### 2. Le VRAI probleme : l'IP affichee etait fausse
Sortie de l'utilisateur :
```
-> http://192.168.100.8:5000     <- affiche en premier
-> http://100.74.55.70:5000
-> http://192.168.100.71:5000
```
Or `ipconfig` + `Get-NetIPAddress` + `getaddrinfo` : la machine n'a QUE
`192.168.100.71` (WiFi) et `100.74.55.70` (Tailscale). **`.8` n'existe pas.**
Et `curl http://192.168.100.8:5000` → rien ; `.71` et `.70` → OK.

Cause : `lan_ips()` faisait `socket.connect(("8.8.8.8", 80))` puis
`getsockname()` pour obtenir « l'IP principale ». Cette valeur peut renvoyer
une adresse **attachee a aucune interface** (bail DHCP perime, route
transitoire). Elle etait mise en premier → l'utilisateur testait forcement la
mauvaise URL.

Correctif :
- `bound_ipv4()` = `getaddrinfo(gethostname())` filtre (pas de 127.x, pas de
  169.254.x APIPA)
- tri : RFC1918 (192.168/10/172.16-31) d'abord, puis 100.x Tailscale
- apres demarrage, `wait_and_check()` interroge `/languages` sur chaque IP
  et n'affiche ✅ que celles qui repondent vraiment
- detection « serveur deja lance » sur le port (evite l'echec waitress)
- affiche l'URL unique a saisir dans l'app

### Le retenir
- `socket.connect(("8.8.8.8",80)) + getsockname()` n'est **pas fiable** pour
  connaitre son IP locale. Toujours croiser avec les IP reellement liees.
- Un `warnings.filterwarnings` peut sembler sans effet si le warning vient
  d'un **autre processus** (ici le parent). Verifier d'ou il part avant
  d'accuser le filtre.
- L'IP du PC **a change** (.8 → .71) : l'URL a saisir dans l'app est
  maintenant `http://192.168.100.71:5000`.

Commit `05f81dd` pousse. Doc `LIBRETRANSLATE.md` reecrite.

## v65 — plantage a la sauvegarde DATA/Statistiques

Symptome : « je selectionne le repertoire, ca quitte directe l'appli ».

### Cause (OutOfMemoryError, pas un bug SAF)
Le backup de l'utilisateur fait **35 740 308 o**. `exportData()` faisait
`btoa(unescape(encodeURIComponent(json)))` sur la totalite, puis le plugin
recevait ce base64 comme **un seul `String` Java** (~96 Mo en UTF-16) + un
`byte[]` decode (~36 Mo), le tout pendant que le selecteur SAF etait affiche.
`AndroidManifest.xml` n'a **pas** `android:largeHeap`. Le pic tombe exactement
au retour du selecteur → « ca quitte des que je choisis le repertoire ».

### Correctif — transfert par morceaux
**SavePickerPlugin.java** (reecrit, +127/-35) :
- `saveAs({name})` ouvre SAF **sans aucune donnee**, cree le document, rend `{token}`
- `writeChunk({token, data64})` ~256 Ko, `finish({token})`, `abort({token})`
- `SESSIONS` est une **map statique** (`ConcurrentHashMap`) : `saveAs` et
  `pickDir` peuvent tourner sur deux instances differentes du plugin si
  l'activite est recreee par le selecteur.

**Shim mobile** (`THEOLOGICUS.html`, shim v34 ~l.235-330) :
- `exportData()` envoie `{filename, text}` sur natif (plus de `data64`) ;
  desktop inchange (`data64`, `app.py`).
- `toUtf8()` via `TextEncoder` (sinon tranches de 8 Ko), `CHUNK = 3*65536`
  (192 Ko → 262 144 caracteres de base64), `writeAll()` recursif,
  `streamToPicker()`.
- Garde-fou ajoute APRES le 1er test : le repli `legacySave` ne sait porter
