## v110 — trois retours de l'utilisateur, trois correctifs

Demande : *« jai inserer la cle api pour elvenlabs, puis cliquer sur tester, ca

### 1. ElevenLabs — le message d'erreur etait avale

`ttsParleDistant` appelait `onErr('moteur-erreur')` et **jetait** le message
reel ; `ttsTester` affichait donc « echec (moteur-erreur) ». L'utilisateur voyait
qu'il echouait, jamais pourquoi — or « cle refusee » et « Voice ID inconnu »
n'appellent pas le meme geste.

- `ttsCauseHttp(moteur, status, corps)` traduit le statut en cause et reprend le

- `onErr(code, detail)` transmet les deux ; la file s'arrete toujours sur le code
  (`ttsErreurFatale` inchange).
- Bouton **Verifier la cle** : `GET /v1/user` (mesure : 401 + `{"detail":
  {"message":"Invalid API key"}}` sur cle invalide) + pastille d'etat.
- **Tester** verifie la cle AVANT de synthetiser.
- CORS n'etait pas en cause : l'API renvoie `access-control-allow-origin: *` et
  `access-control-allow-headers: *` (mesure au preflight OPTIONS).

Preuve : appel reel avec une cle fausse -> `clé API refusée (401) — Invalid API
key`. Banc `_tts/bench_v109_moteurs.js` etendu (section 3b), **0 echec**.

### 2. Demarrage automatique du service (Windows)

Le bon point d'ancrage etait deja la : `proxy_server.py` gere tout le cycle de
vie d'un service local pour LibreTranslate, et l'app l'appelle en **same-origin**
(`fetch('/libretranslate/start', {method:'POST'})`). Reproduit plutot que
reinvente :

- `proxy_server.py` : `ST_PORT = 8091`, `_st_health`, `st_status`, `st_start`,

- **L'interpreteur est choisi en le testant** (`import numpy, onnxruntime`) :
  `sys.executable`, puis `py -3`, `python`, `python3`. Le message d'echec donne
  l'interpreteur et la commande exacte.
- **`ready` exige `loaded: true`** dans `/health`, pas seulement un port qui
  repond : annoncer « en ligne » sur un port ouvert ferait echouer la premiere
  lecture pendant le chargement du modele.
- Case « Demarrer automatiquement au lancement » (cochee par defaut) + bouton
  demarrer/arreter + journal lisible dans l'app.
- `build_installer.bat` livre `tools/start_supertonic.py` et `tools/supertonic/`.

Preuve : `_tts/test_service_supertonic.py` -> **0 echec**, service pret en 1 s,
WAV de 114 916 octets (RIFF) rendu, arret propre.

**`proxy_server.py` est compile DANS l'exe** : le demarrage automatique exige un
nouvel exe, pas seulement un HTML a jour. Chaine de build locale disponible
(`py -3.12` + PyInstaller 6.22.3, ISCC, PFX de signature present).

## Lecons durables

- **Un message d'erreur qui ne dit pas la cause est un defaut, pas un detail.**
  « echec (moteur-erreur) » a coute un aller-retour utilisateur.
- **Chercher le mecanisme existant avant d'en ecrire un second.** LibreTranslate
  avait deja tout : cycle de vie, routes, UI, decouverte de Python.
- **`ready` != `running`.** Un port ouvert n'est pas un service pret.

## v110 — le build Windows, et pourquoi il ne tournait pas

Le demarrage automatique vit dans `proxy_server.py`, donc dans l'exe. Sans
nouvel exe, tout le travail v110 restait invisible sur la machine. Le build
etait bloque : **aucun fichier `.bat` ne s'execute dans l'environnement de
l'agent.**

Mesure, pas supposition : `cmd.exe` est refuse par l'outil Bash (« bypasse toute
validation de commande ») **et** par l'outil PowerShell ; PowerShell refuse en
plus de mettre un `.bat` dans un pipeline (`CantActivateDocumentInPipeline`) ;
enfin un `_test_bat.bat` minimal (3 lignes, ecrit un fichier preuve) lance depuis
PowerShell **n'a produit aucun fichier preuve**. Le `.bat` n'a jamais tourne.

### La sortie : rejouer les etapes directement

`tools/build_windows.py` reproduit `build_installer.bat` etape par etape et
s'execute, lui, partout ou il y a un interpreteur. Les deux scripts doivent
rester en phase. `py -3.12` est resolu par `sys.executable` (le script est lance
par `py -3.12`), ce qui evite tout probleme de `py` introuvable.

### Trois pieges du build, tous mesures

1. **Le garde-fou de suppression en masse bloque le build lui-meme.** Un
   `shutil.rmtree` sur `build/THEOLOGICUS` (377 cibles) est refuse
   (`SAFE_DELETE_BULK_CONFIRM_REQUIRED`, seuil 50), **et PyInstaller s'y fait
   prendre aussi** : son etape COLLECT fait « Removing dir dist\THEOLOGICUS »
   (2961 cibles) et meurt. Solution : **renommer au lieu de supprimer**, et
   surtout **avant** PyInstaller — COLLECT trouve alors un `dist\THEOLOGICUS`
   inexistant, donc cree un dossier vierge. Effet secondaire heureux : plus
   aucun fichier perime, l'etape de purge devient inutile. C'est plus propre que
   le `.bat`, qui purge apres coup.
2. **`_internal` : 44 fichiers perimes a la mise a jour en place**, tous des
   `api-ms-win-*-l1-1-0.dll` (stubs d'API-set que PyInstaller ne livre plus).
   Mesure : l'ancien a 301 fichiers, le nouveau 257, et **aucun fichier du
   nouveau n'est absent de l'ancien**. Inoffensifs -> pas d'`[InstallDelete]`
   ajoute a `installer.iss`. Decision mesuree, pas precaution.
3. **`script` dans `/supertonic/status` est un BOOLEEN, pas un chemin** :
   `os.path.isfile(_st_script())`. C'est le contrat du JS, qui teste
   `!etat.script`. Mon premier banc l'avait suppose chemin — c'est le banc qui
   etait faux, pas le code.

## v111 — « **gras** » en clair dans certaines puces

Defaut signale dans les videos de l'utilisateur, laisse ouvert en v110. Le
convertisseur **existait** (`inlineMd` : `\*\*([^*]+)\*\*` -> `<strong>`) :
lire le source ne suffisait donc pas a trouver la cause.

### La methode qui a trouve

`_tts/bench_gras.js` appelle le **vrai `mdToHtml`** dans un vrai Chrome et
mesure 34 constructions de puce. **Bilan initial : 8 echecs, une seule cause.**

### La cause : le rendu se fait en DEUX passes

Le texte entre guillemets (`«…»`, `"…"`) et les mentions `Source : …`,
`Selon …`, `D'après …`, `cf. …` sont **extraits en jetons** (`@@BCIT`, `@@BSRC`)
**AVANT** le rendu, puis **restaures APRES `inlineMd`**. Leur contenu n'a donc
jamais traverse les regles d'emphase : des que le gras tombait **a l'interieur**
d'une citation, l'utilisateur voyait les asterisques.

- **`mdEmphase(s)`**, fonction **nommee**, appelee par `inlineMd` **et** par le
  site de restauration. **Tout site qui restaure du texte brut doit l'appeler.**
- `[^*]+` -> `[\s\S]+?` : `**a * b**` contient un asterisque, l'ancien motif le
  laissait intact. Meme symptome, autre cause.
- Les quatre captures `Source`/`Selon`/`D'après`/`cf.` excluent `*`
  (`[^\n,;*]+`). Sans cela, `**Source : Saint Augustin**` etait capture jusqu'au
  `**` fermant **compris**, laissant l'ouvrant orphelin hors du span :
  `**<span class="bible-source">Source : Saint Augustin**</span>`.
- Les quatre regles **jumelles** dans `inlineMd` sont **inatteignables** (le
  pre-passage tokenise toujours en premier) mais restent alignees : **deux sites
  divergents, c'est le piege classique de ce fichier**.

Apres : **34/34, 0 echec**. `check_syntax.js` OK (59 blocs), **LF preserve**.
Windows reconstruit en **2.0.131**, exe installe re-verifie (**23 controles, 0
echec**), `_inst_v102` **identique octet pour octet** a `dist/THEOLOGICUS`.

### Deux reflexes a garder

- **Un rendu en deux passes est un piege structurel** : tout contenu extrait en
  jeton contourne les regles inline. Quand un marqueur survit « par endroits »,
  chercher ce qui est extrait, pas ce qui est converti.
- **Ne pas conclure « le convertisseur existe donc c'est autre chose »** : le
  motif existait, il n'etait simplement jamais applique a ce contenu-la.

### Hygiène

`_inst_*` et `_bak_*` ajoutes a `.gitignore` : `_inst_v102` est un dossier
d'installation de ~230 Mo non suivi qu'un `git add -A` aurait avale. Ecrit en
**binaire** pour conserver le CRLF de `.gitignore` (un ecrit en LF avait deja
produit un diff parasite de 139 lignes).

### Bug #2 — LibreTranslate « Démarrer » : cause racine CORRIGÉE

**Hypothese initiale (fausse) :** `_lt_python_cmd()` choisissait `py -3`
(= Python 3.14) qui n'aurait pas `libretranslate`. **Mesure contraire :**
`import libretranslate` reussit en 3.14 ET en 3.12. Le vrai defaut, lu dans
`logs/libretranslate.log` : `No module named libretranslate.__main__ ;
'libretranslate' is a package and cannot be directly executed`. Le paquet
n'a PAS de `__main__.py`, donc `py -m libretranslate` echoue toujours —
quelle que soit la version Python. Le point d'entree est le **module**
`libretranslate.main` (ou le script `libretranslate.exe`). `tools/start_libretranslate.py`
utilisait deja `from libretranslate.main import main; main()` (depuis v63) :
seul le chemin dans l'exe (`proxy_server.py` -> `lt_start`) etait casse.

Correctif `proxy_server.py` (compile DANS l'exe -> **nouvel exe requis**) :
- `lt_start()` : `py -m libretranslate` -> `py -m libretranslate.main`.
- `_lt_python_cmd()` : sonde chaque candidat avec `import libretranslate.main`
  (miroir de `_st_python_cmd`), garde le premier qui reussit, met en cache
  `_lt["python"]`.
- `_lt_installed()` : delegue a `_lt_python_cmd()` (qui prouve deja
  l'import). `lt_install()` re-sonde aussi l'interpreteur.

Preuve **execution** (pas lecture) :
- `_tts/bench_libretranslate_src.py` : importe le proxy source, `lt_start()` ->
  `HTTP /languages` 200, `lt_stop()` propre. VERDICT OK.

- `_tts/bench_libretranslate_exe.py` sur `_inst_v102/THEOLOGICUS.exe` (2.0.136) :
  `POST /libretranslate/start` -> 200, service `ready`, `/languages` 200. VERDICT
  correctif actif dans l'exe livre.

Deploy : `robocopy /E` (paths Windows + `MSYS_NO_PATHCONV=1`, sinon Git Bash
mangle `/E` en `E:/`) de `dist/THEOLOGICUS` -> `_inst_v102` ; backup de l'ancien

### Lecon durable — ne pas deviner la cause d'un `-m` qui echoue

### Regression immediate — ReferenceError au premier chargement

Bandeau rouge signale : `ReferenceError: narration is not defined` dans
`preloadNotice`. Cause : mon `replace_all` sur la sous-chaine
`getVoiceForLang('francais')` -> `getVoiceForLang('francais', { narration })`
a aussi touche **3 sites hors de `makeUtterance`** (`preloadFrVoice` fallback,

ajoute un identifiant en portee doit etre verifiee site par site**, ou
preferee en explicite (`{ narration: ttsNarration() }`) des la conception.


## v114 — accents respectés + « ton théologique »

Demande : *« je veux que les accents se respectent (théologie, patristique,
archéologie…) ; les voix manquent de rassurance théologique, d'émotions, de ton
pour certains mots ; ex. plus imposant / plus lent ton explicatif. Échantillon
ElevenLabs : Émilie - Customer service advisor. »*

### Accents — diagnostic
Le pipeline texte (`cleanMd` -> `prosodyPreprocess`) **conserve** les accents ;
les regex `[\u0300-\u036F]` qui existent ne concernent que l'appariement
recherche/référence, pas le TTS. `normalizeTranslitSpeech` fait NFC en étape 1
(donc protège). Cause réelle des accents mal lus = **le moteur de voix** :
voix système en repli anglais (cas v108, pas de pack FR installé) ou voix non
française. Ajout défensif : **NFC** du texte envoyé à chaque moteur
(`makeUtterance` + `ttsParleDistant`) — les accents décomposés (NFD) sont
recomposés en précomposé, que tout moteur prononce.

### Ton théologique (ttsTonTheologique)
 fonction pure, marqueurs FR -> profil prosodie :
- **solennel** (citation «…», « Ainsi parle le Seigneur », « Écoutez »,
  Alléluia/Amen, « car il est écrit », « Gloire à Dieu », « jugement »,
  « Jésus-Christ ») : rate ×0.82, pitch −0.06, vol 1.
- **rassurant** (« ne crains pas », « paix », « grâce », « Dieu est amour »,
  « repos », « je suis avec vous »…) : rate ×0.92, pitch +0.03, vol 0.96.
- **explicatif** (« c'est-à-dire », « par exemple », « en d'autres termes »…) :
  rate ×0.95. Neutre = 1/0/1.
Applique : systeme (rate/pitch/volume par segment) + Supertonic (speed par
segment, plancher 0.8). ElevenLabs : pas de réglage de débit par voice_settings
(style seulement, deja 0.4 en narration) ; une vraie émotion mot-à-mot exigerait
du SSML `<prosody>` (eleven_v3). Banc `verify_ton.js` **10/10**.

Conseil utilisateur (hors code) : pour la « rassurance » ElevenLabs, utiliser
une voix FR chaude — ex. **Émilie** (l'échantillon qu'il cite) — en collant son
Voice ID dans Réglages -> LECTURE VOCALE -> ☁ ElevenLabs -> Voice ID.

Commit `56100b9` (push `b36df9d..56100b9`), **2.0.140**.

## v115 — « l'app se ferme au bout d'une minute » : la mise à jour automatique

Signalé : *« je lance puis après une minute ça ferme l'appli »*.

**Ce n'est PAS un plantage.** Preuves, pas suppositions :

- `%TEMP%\THEOLOGICUS-Setup-x64.exe` — **46,5 Mo téléchargés à 15:54**.
- `_inst_v102\unins\unins000.exe` + `.dat` **écrits à 15:54** → un installateur
  Inno a tourné à ce moment-là.
- Traceback `app.py:81 in install_update` (un autre essai, lui, a 404).
- `THEOLOGICUS.log` : **aucune erreur fatale** — `/config` répond 200 en GET
  **et** en POST jusqu'à la dernière ligne, le serveur n'est jamais tombé.

Cause : **la mise à jour automatique intégrée (v74)**. `DesktopApi.install_update`
télécharge l'installateur, le lance (`os.startfile`), puis
`threading.Timer(2.0, fermer)` **détruit la fenêtre 2 s plus tard** pour que
l'installateur puisse écraser les fichiers en cours d'usage (`app.py` 91-101).
L'app qui « se ferme tout seul » est donc le comportement **voulu**.

Déclencheur ici : mes pushs venaient de porter le dépôt à 2.0.142 alors que
l'installé était 2.0.140 (construit *avant* les commits).

### Deux conséquences à retenir

1. **Chaque push déclenche une mise à jour automatique chez l'utilisateur**, donc
   une fermeture de l'app au lancement suivant. Normal — à expliquer plutôt qu'à
   « corriger ».
2. **Le CI construit AUSSI l'installateur Windows**, pas seulement l'APK : le run
   s'appelle « Build Android APK » mais `_inst_v102` est passé en **2.0.141**
   (build CI de mon commit) après la réinstallation. Ne pas se fier au nom du job.

Correctif **survivant** à la réinstallation, vérifié sur l'exe installé :
`GET /config` → 200, `GET /theologicus-keys` → 200, HTML servi 200.

### Leçon durable — ne JAMAIS écrire dans un magasin réel pour vérifier

Mon banc a fait un `POST /config` sur l'exe installé : il a **écrasé la vraie
config** de l'utilisateur (clé ElevenLabs + voix). Le `GET` précédent l'avait
lue, j'ai pu la restaurer trait pour trait — mais c'est une erreur de méthode.
**Règle : sonder une configuration en LECTURE SEULE, ou sur un magasin jetable.
Un banc qui écrit détruit exactement la preuve qu'il prétend rapporter.**

## v117 — « il me redemande ma clé API à chaque lancement » : c'était le PORT

Symptôme : à chaque lancement ou mise à jour sous Windows, l'utilisateur devait
ressaisir sa clé API et refaire sa configuration avant d'accéder à l'interface.

**Cause racine : le port, pas le stockage.** Une origine, c'est
`scheme://hote:port`. Deux ports = deux origines = **deux stockages navigateur
distincts** (localStorage, IndexedDB, cookies). `app.py` appelait `pick_port()`,
qui faisait `bind(("127.0.0.1", 0))` dès que 8765 était pris — et un bind sur le
port 0 rend un port **pseudo-aléatoire**. Les fichiers durables n'ont jamais été
en cause : le log montrait `GET /theologicus-keys 200` et `GET /config 200` à
chaque lancement.

Mesure sur la machine, sans deviner : `python.exe serve.py` (PID 18096) occupait
**8765, 8766 et 8767** ; `THEOLOGICUS.exe` (PID 23248) écoutait sur **61568**. Le
port aléatoire n'étant pas reproductible, le symptôme paraissait intermittent —
d'où « à chaque fois » plutôt que « toujours ».

**Correctifs**
1. Port **déterministe** : plage 8765–8780, premier port libre. Plus aucun
   repli aléatoire.
2. **Réutilisation d'instance** : sonde `/__theologicus_ping` + repli sur le
   contenu de `THEOLOGICUS.html` (pour reconnaître une instance d'un ancien exe).
3. Le port est **journalisé** — sans lui le symptôme était indiagnosticable.
4. **Garde de build** : `copier()` refuse d'écraser une cible plus grosse.

**Deux pièges rencontrés**
- Le profil WebView2 est bien **persistant** (`%APPDATA%/pywebview`, car
  `private_mode=False`) — vérifié dans `init_storage()` de pywebview. Le port
  était donc toute l'histoire.
- **`sync_html.py` criait « PERIMEE » à tort** : le build **estampe** la version
  dans `dist`/`_inst_v102` (`var STAMPED = '__THEO_VERSION__'` → `'2.0.145'`),
  soit 9 octets de MOINS que la source. J'ai « corrigé » cet écart plusieurs fois
  avant de comprendre. `sync_html.py` reconnaît désormais le tampon.

Banc `_v117/verify_port.py` : **10/10**. Vérifié sur le binaire déployé : ports
8765-8767 squattés → THEOLOGICUS.exe a pris **8768** (un cran dans la plage, pas
un tirage), sonde = `{"app":"theologicus"}`. Commit `c002857` (2.0.146), poussé.
