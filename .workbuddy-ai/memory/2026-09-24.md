# THEOLOGICUS — 2026-09-24

## v110 — trois retours de l'utilisateur, trois correctifs

Demande : *« jai inserer la cle api pour elvenlabs, puis cliquer sur tester, ca
me dit ElevenLabs : échec (moteur-erreur). et pour surpertonic, je voudrais que
quand je lance Theologicus, ca demare automatiquement et en meme temps le
serveur pour supertonic... et je vux savoir comment faire pour lancer supertonic
sur mon android »*.

### 1. ElevenLabs — le message d'erreur etait avale

`ttsParleDistant` appelait `onErr('moteur-erreur')` et **jetait** le message
reel ; `ttsTester` affichait donc « echec (moteur-erreur) ». L'utilisateur voyait
qu'il echouait, jamais pourquoi — or « cle refusee » et « Voice ID inconnu »
n'appellent pas le meme geste.

- `ttsCauseHttp(moteur, status, corps)` traduit le statut en cause et reprend le
  `detail.message` de l'API.
- `onErr(code, detail)` transmet les deux ; la file s'arrete toujours sur le code
  (`ttsErreurFatale` inchange).
- Bouton **Verifier la cle** : `GET /v1/user` (mesure : 401 + `{"detail":
  {"message":"Invalid API key"}}` sur cle invalide) + pastille d'etat.
- **Tester** verifie la cle AVANT de synthetiser.
- CORS n'etait pas en cause : l'API renvoie `access-control-allow-origin: *` et
  `access-control-allow-headers: *` (mesure au preflight OPTIONS).

Preuve : appel reel avec une cle fausse -> `clé API refusée (401) — Invalid API
key`. Banc `_tts/bench_v109_moteurs.js` etendu (section 3b), **0 echec**.

### 2. Demarrage automatique du service (Windows)

Le bon point d'ancrage etait deja la : `proxy_server.py` gere tout le cycle de
vie d'un service local pour LibreTranslate, et l'app l'appelle en **same-origin**
(`fetch('/libretranslate/start', {method:'POST'})`). Reproduit plutot que
reinvente :

- `proxy_server.py` : `ST_PORT = 8091`, `_st_health`, `st_status`, `st_start`,
  `st_stop`, et les routes `/supertonic/status|start|stop|log`.
- **L'interpreteur est choisi en le testant** (`import numpy, onnxruntime`) :
  `sys.executable`, puis `py -3`, `python`, `python3`. Le message d'echec donne
  l'interpreteur et la commande exacte.
- **`ready` exige `loaded: true`** dans `/health`, pas seulement un port qui
  repond : annoncer « en ligne » sur un port ouvert ferait echouer la premiere
  lecture pendant le chargement du modele.
- Case « Demarrer automatiquement au lancement » (cochee par defaut) + bouton
  demarrer/arreter + journal lisible dans l'app.
- `build_installer.bat` livre `tools/start_supertonic.py` et `tools/supertonic/`.

Preuve : `_tts/test_service_supertonic.py` -> **0 echec**, service pret en 1 s,
WAV de 114 916 octets (RIFF) rendu, arret propre.

**`proxy_server.py` est compile DANS l'exe** : le demarrage automatique exige un
nouvel exe, pas seulement un HTML a jour. Chaine de build locale disponible
(`py -3.12` + PyInstaller 6.22.3, ISCC, PFX de signature present).

### 3. Android — reponse documentee, pas codee

Faits verifies dans le depot, pas supposes :

- Le shim v53 fournit `window.speechSynthesis` **et** `SpeechSynthesisUtterance`
  au-dessus du plugin natif `SpeechBridge` (moteur Google du telephone), avec
  `getVoices()` rendant une voix `fr-FR`. **Donc Android lit deja le francais** —
  contrairement a ce PC Windows. Rien a installer cote app ; il faut les donnees
  vocales francaises du moteur Google.
- `android:usesCleartextTraffic="true"` **et** `allowMixedContent: true` sont deja
  en place : le telephone peut joindre le service du PC en HTTP sur le LAN.
- Le service ecoute deja sur `0.0.0.0` et affiche l'IP LAN au demarrage. Le piege
  est l'URL par defaut `127.0.0.1:8091`, qui designe le telephone : il faut l'IP
  du PC.
- Embarquer Supertonic dans l'APK n'est pas realiste : helper navigateur
  (`web/helper.js`, ONNX Runtime Web) mais **385 Mo** de modele a servir et
  WebGPU non garanti dans un WebView Android.

## Lecons durables

- **Un message d'erreur qui ne dit pas la cause est un defaut, pas un detail.**
  « echec (moteur-erreur) » a coute un aller-retour utilisateur.
- **Chercher le mecanisme existant avant d'en ecrire un second.** LibreTranslate
  avait deja tout : cycle de vie, routes, UI, decouverte de Python.
- **`ready` != `running`.** Un port ouvert n'est pas un service pret.

## v110 — le build Windows, et pourquoi il ne tournait pas

Le demarrage automatique vit dans `proxy_server.py`, donc dans l'exe. Sans
nouvel exe, tout le travail v110 restait invisible sur la machine. Le build
etait bloque : **aucun fichier `.bat` ne s'execute dans l'environnement de
l'agent.**

Mesure, pas supposition : `cmd.exe` est refuse par l'outil Bash (« bypasse toute
validation de commande ») **et** par l'outil PowerShell ; PowerShell refuse en
plus de mettre un `.bat` dans un pipeline (`CantActivateDocumentInPipeline`) ;
enfin un `_test_bat.bat` minimal (3 lignes, ecrit un fichier preuve) lance depuis
PowerShell **n'a produit aucun fichier preuve**. Le `.bat` n'a jamais tourne.

### La sortie : rejouer les etapes directement

`tools/build_windows.py` reproduit `build_installer.bat` etape par etape et
s'execute, lui, partout ou il y a un interpreteur. Les deux scripts doivent
rester en phase. `py -3.12` est resolu par `sys.executable` (le script est lance
par `py -3.12`), ce qui evite tout probleme de `py` introuvable.

### Trois pieges du build, tous mesures

1. **Le garde-fou de suppression en masse bloque le build lui-meme.** Un
   `shutil.rmtree` sur `build/THEOLOGICUS` (377 cibles) est refuse
   (`SAFE_DELETE_BULK_CONFIRM_REQUIRED`, seuil 50), **et PyInstaller s'y fait
   prendre aussi** : son etape COLLECT fait « Removing dir dist\THEOLOGICUS »
   (2961 cibles) et meurt. Solution : **renommer au lieu de supprimer**, et
   surtout **avant** PyInstaller — COLLECT trouve alors un `dist\THEOLOGICUS`
   inexistant, donc cree un dossier vierge. Effet secondaire heureux : plus
   aucun fichier perime, l'etape de purge devient inutile. C'est plus propre que
   le `.bat`, qui purge apres coup.
2. **`_internal` : 44 fichiers perimes a la mise a jour en place**, tous des
   `api-ms-win-*-l1-1-0.dll` (stubs d'API-set que PyInstaller ne livre plus).
   Mesure : l'ancien a 301 fichiers, le nouveau 257, et **aucun fichier du
   nouveau n'est absent de l'ancien**. Inoffensifs -> pas d'`[InstallDelete]`
   ajoute a `installer.iss`. Decision mesuree, pas precaution.
3. **`script` dans `/supertonic/status` est un BOOLEEN, pas un chemin** :
   `os.path.isfile(_st_script())`. C'est le contrat du JS, qui teste
   `!etat.script`. Mon premier banc l'avait suppose chemin — c'est le banc qui
   etait faux, pas le code.

### Verification : l'exe lui-meme, pas le source

`_tts/verifie_exe.py` lance l'exe **reel** en mode `THEOLOGICUS_NO_WINDOW=1` et
interroge les routes. Deux pieges evites : un port ferme repond **502** ici (donc
`curl && echo OK` est un faux positif), et **chaque invocation shell a son propre
espace reseau** — un exe lance dans une invocation n'est pas joignable depuis la
suivante, donc lancement et sondage tiennent dans un seul processus.

Resultat : **23 verifications, 0 echec**. `/supertonic/status` -> 200,
`script: true` (le service est trouve a cote de l'exe), `deps: true`,
`port: 8091` ; `/libretranslate/status` -> 200 (non-regression) ; `POST
/supertonic/stop` -> 200 ; le HTML servi est l'application, version tamponnee.

### Le piege de livraison : l'installation reelle n'est pas celle qu'on croit

Le raccourci du Bureau pointe sur **`C:\Theologicus\_inst_v102\THEOLOGICUS.exe`**
(pas `%LOCALAPPDATA%\Programs\THEOLOGICUS`, qui est reste en 2.0.94). Le
registre Inno confirme : `{7C1E2A44-...}_is1`, version 2.0.128, installe a
`C:\Theologicus\_inst_v102\`. **Le lanceur de l'utilisateur est donc `_inst_v102`,
et son exe n'avait pas les routes.**

- `Get-Process -Name THEOLOGICUS` rend **vide** alors que l'app tourne : l'outil

  a l'ecriture. Ne jamais conclure « rien ne tourne » d'un `Get-Process` vide.
- Le renommage de `_inst_v102\_internal` echoue (`WinError 5`) et la copie de

  a jour, exe et runtime anciens). L'installateur Inno la finira en place.

Livrables : `dist/THEOLOGICUS-Setup-x64.exe` et `output/THEOLOGICUS-Setup-x64.exe`
(48 302 352 octets, **2.0.130**, signes), `output/THEOLOGICUS.exe` (5 587 456).
Retour arriere : `_bak_v128/THEOLOGICUS.exe`.

## v111 — « **gras** » en clair dans certaines puces

Defaut signale dans les videos de l'utilisateur, laisse ouvert en v110. Le
convertisseur **existait** (`inlineMd` : `\*\*([^*]+)\*\*` -> `<strong>`) :
lire le source ne suffisait donc pas a trouver la cause.

### La methode qui a trouve

`_tts/bench_gras.js` appelle le **vrai `mdToHtml`** dans un vrai Chrome et
mesure 34 constructions de puce. **Bilan initial : 8 echecs, une seule cause.**

### La cause : le rendu se fait en DEUX passes

Le texte entre guillemets (`«…»`, `"…"`) et les mentions `Source : …`,
`Selon …`, `D'après …`, `cf. …` sont **extraits en jetons** (`@@BCIT`, `@@BSRC`)
**AVANT** le rendu, puis **restaures APRES `inlineMd`**. Leur contenu n'a donc
jamais traverse les regles d'emphase : des que le gras tombait **a l'interieur**
d'une citation, l'utilisateur voyait les asterisques.

- **`mdEmphase(s)`**, fonction **nommee**, appelee par `inlineMd` **et** par le
  site de restauration. **Tout site qui restaure du texte brut doit l'appeler.**
- `[^*]+` -> `[\s\S]+?` : `**a * b**` contient un asterisque, l'ancien motif le
  laissait intact. Meme symptome, autre cause.
- Les quatre captures `Source`/`Selon`/`D'après`/`cf.` excluent `*`
  (`[^\n,;*]+`). Sans cela, `**Source : Saint Augustin**` etait capture jusqu'au
  `**` fermant **compris**, laissant l'ouvrant orphelin hors du span :
  `**<span class="bible-source">Source : Saint Augustin**</span>`.
- Les quatre regles **jumelles** dans `inlineMd` sont **inatteignables** (le
  pre-passage tokenise toujours en premier) mais restent alignees : **deux sites
  divergents, c'est le piege classique de ce fichier**.

Apres : **34/34, 0 echec**. `check_syntax.js` OK (59 blocs), **LF preserve**.
Windows reconstruit en **2.0.131**, exe installe re-verifie (**23 controles, 0
echec**), `_inst_v102` **identique octet pour octet** a `dist/THEOLOGICUS`.

### Deux reflexes a garder

- **Un rendu en deux passes est un piege structurel** : tout contenu extrait en
  jeton contourne les regles inline. Quand un marqueur survit « par endroits »,
  chercher ce qui est extrait, pas ce qui est converti.
- **Ne pas conclure « le convertisseur existe donc c'est autre chose »** : le
  motif existait, il n'etait simplement jamais applique a ce contenu-la.

### Hygiène

`_inst_*` et `_bak_*` ajoutes a `.gitignore` : `_inst_v102` est un dossier
d'installation de ~230 Mo non suivi qu'un `git add -A` aurait avale. Ecrit en
**binaire** pour conserver le CRLF de `.gitignore` (un ecrit en LF avait deja
produit un diff parasite de 139 lignes).
