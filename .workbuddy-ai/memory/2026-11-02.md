# 2026-11-02 — Backup des conversations (v679 → v680)

## Contexte
L'utilisateur utilise l'app desktop Windows (WebView2) et a signalé deux échecs
de « TÉLÉCHARGER TOUTES LES DONNÉES » :
1. Succès mensonger, aucun fichier dans `backups/` (v678/v679).
2. Crash « Out of memory » de la WebView (screenshot 221820.png) — v680 en cours.

## v679 (déjà publié en v4.0.708)
- Cause du succès mensonger : `btoa(unescape(encodeURIComponent(json)))` sur
  50+ Mo → pic mémoire, connexion avortée côté serveur (WinError 10053 dans
  THEOLOGICUS.log) ; le repli `a.click()` blob échoue SILENCIEUX en WebView.
- Fix : serveur (`proxy_server._save_data`) accepte désormais le JSON BRUT
  (`text`), le client envoie du texte brut sur desktop, repli honnête (toast
  erreur + révélation du dossier `backups/`) au lieu d'un faux succès.
- Confirmé : les backups du 28–30 oct sont INTACTS dans `backups/`.

## v680 (en cours de commit — corrige l'« Out of memory »)
- Même un JSON brut de 50+ Mo sature le rendu WebView.
- Export DÉCoupÉ en morceaux de 2 Mo : client (`exporterParMorceaux` dans
  `exportData()`) envoie chaque morceau en base64 (mémoire bornée à un seul
  morceau) ; serveur (`_save_data`, mode `chunk`/`index`/`total`) concatène en
  binaire via `.part` puis `os.replace` atomique sur le dernier.
- JSON compact (`JSON.stringify(payload)` sans indentation) pour réduire le
  volume.
- DÉCOUPE SÛRE : `decouperSurs` recule d'un code unit si la frontière tombe
  sur un substitut HAUT (emoji/CJK) — sinon `encodeURIComponent` lève
  « malformed URI » et le morceau échoue (perte silencieuse). Vérifié :
  partition contiguë et complète, réassemblage binaire identique.
- Bancs de régression : assemblage chunké 4,16 Mo / 2 morceaux identique au
  payload ; `text` brut et `data64` toujours OK ; aucun morceau ne se termine
  sur un substitut haut orphelin.
