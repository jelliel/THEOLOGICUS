# 2026-09-22 — L'infobulle hébreu se refermait au clic

## Le symptôme rapporté

Fatih : après avoir installé `THEOLOGICUS-Setup-x64.exe`, il ouvre une
référence biblique, le panneau s'affiche, mais **dès qu'il clique sur un mot
hébreu, l'infobulle disparaît**.

## Deux causes distinctes, toutes deux réelles

J'ai d'abord supposé une seule cause. Il y en avait **deux**, et la seconde
explique à elle seule pourquoi il n'a jamais vu la ligne hébraïque.

### 1. L'installeur livré n'avait pas le corpus hébreu

`dist/THEOLOGICUS/` datait du **16 septembre** et ne contenait que
`bible`, `quran`, `tafsir`, `libs` — soit l'état du repo six jours plus tôt.
`biblehb/` (créé le 20) était **absent**, donc `__ensureBibleHb` recevait un
404 et aucune ligne hébraïque n'était injectée. `version.txt` annonçait
`1.0.33`, ce qui trahissait l'âge du dossier.

Ce n'est **pas** un défaut des listes d'empaquetage : `COPY_DIRS`,
le job `windows` de la CI et `build_installer.bat` listaient bien les 16
corpus. C'est le `dist/` local qui est un **vestige qui ne se régénère pas
tout seul**. Leçon : **purger `dist/THEOLOGICUS` avant tout rebuild**, sinon
on mesure et on livre l'ancien contenu sans le moindre avertissement.

### 2. Le panneau se refermait à l'entrée de la souris dans le mot

Reproduit dans Chrome avec de **vrais** événements souris (CDP
`Input.dispatchMouseEvent`), pas des `dispatchEvent` synthétiques. La trace
des écouteurs est sans ambiguïté :

```
CAPTURE-OUT cible=span.bible-ref related=span.hb dansTip=false versTip=true
```

Le mot à mot vit **dans** le panneau `#bible-verse-tip`. Passer du lien vers
un mot déclenche donc `mouseout` sur le lien, avec `relatedTarget` = le mot.
Le test d'origine était :

```js
document.addEventListener('mouseout', function (e) {
  const el = e.target.closest('a.bible-ref, span.bible-ref');
  if (el) hideTip();          // ← le mot n'est ni a.bible-ref ni span.bible-ref
});
```

Le mot n'ayant aucune de ces deux classes, `hideTip()` partait **au moment
précis où l'on entrait dans le panneau**, emportant la fiche du mot avec lui.
Ce n'était donc pas « au clic » : ça fermait dès le survol, et le clic ne
faisait que confirmer la disparition.

Deuxième trou de la même famille, sur le `click` en capture :

```js
if (!el) { closeTip(); return; }   // ← n'importe quelle cible non-lien ferme tout
```

### Correctif (v93)

Un seul prédicat, `dansPanneau(n) = tip.contains(n)`, appliqué au `target` du
`click` et au `relatedTarget` du `mouseout` (ainsi qu'au `target` du
`mouseout`). **Règle générale à retenir : un conteneur qui s'ouvre au survol
doit tester `relatedTarget`, jamais la seule classe du `target`.**

Note : le `click` de v89 fait déjà `stopPropagation()` en capture, ce qui
suffisait à protéger les mots hb d'un `closeTip()` — mais **seulement**
hb/gr, et rien ne protégeait le `mouseout`.

## Renforcement de `tools/stamp_version.py` et de `build_installer.bat`

`tools/stamp_version.py` retombait **silencieusement** sur le `VERSION` racine,
périmé à 1.0.10. Il **avertit désormais bruyamment** et refuse de tamponner une
version vide.

**Cause du `1.0.33` enfin établie et chiffrée.** Le `for /f` de
`build_installer.bat` :

```bat
set "VER=2.0.0"
for /f %%i in ('git rev-list --count HEAD 2^>nul') do set "VER=2.0.%%i"
```

Si la commande interne échoue, **le corps de la boucle ne s'exécute jamais** :
`VER` n'est pas écrasé, il garde `2.0.0` — puis `stamp_version.py` reçoit
`2.0.0`, ne trouve pas `__THEO_VERSION__` dans un HTML **déjà tamponné**, et
écrit quand même `version.txt`.

Preuve : le build de `dist` datait du **16/09 17:09**, le dernier commit de ce
moment est `cd3b75b` (« v61: translate typed chat text… »), et
`git rev-list --count cd3b75b` = **38**. Le build aurait dû s'annoncer
**2.0.38**. Il annonçait **1.0.33** — soit exactement l'ancien `version.txt`
laissé par un build antérieur, jamais écrasé. (Le HTML de `dist` contenait bien
`STAMPED = '1.0.33'`, il n'était donc pas question d'un simple numéro de
commits mal calculé.)

`VER` démarre désormais **vide** et le script **abandonne** avec un message
explicite si git ne répond pas, au lieu de compiler sous une version fausse.
`dist\THEOLOGICUS` est **purgé avant d'être repeuplé** (même piège que
`dist/THEOLOGICUS/version.txt` : les restes d'un build précédent partent dans
l'installeur), et PyInstaller est appelé **sans `--clean`** avec une suppression
préalable de `build\THEOLOGICUS`.

Non pu activer/verifier cette logique par un test direct : `cmd.exe` depuis
Bash et depuis PowerShell est bloqué par la sécurité. Le raisonnement tient
toutefois sur des faits vérifiés (dates, comptes de commits, contenu du HTML).

### v95 (`2e167f3`) — un span VIDE de 3 px avalait le clic

**Cause réelle, mesurée et reproduite.** Une sélection qui commence (ou finit)
exactement sur la **frontière d'un nœud texte** produit une tranche vide.
Mesuré sur `Le <strong>Seigneur</strong>` : la plage commence à l'offset 3 du
nœud texte `"Le "`, soit sa longueur. La branche multi-nœuds appelle alors
`surroundContents` sur une tranche vide et insère :

```
<span data-hl-id=X></span><strong><span data-hl-id=X>Seigneur</span></strong>
```

Deux spans portent le même `data-hl-id`, le **premier est vide et large de
3 px**. `querySelector('[data-hl-id]')` rend le vide : c'est lui que le clic
atteint. L'annotation *est* posée, elle paraît morte.

Voilà pourquoi le symptôme est asymétrique : une **phrase** produit plusieurs
spans larges, le vide se noie dedans ; un **mot** n'a qu'un vrai span, et le
vide de 3 px est collé juste à côté de lui.

Correctif :
- `if (r.collapsed || r.startOffset === r.endOffset) continue;` avant d'enrouler ;
- « déjà posé » n'accepte plus qu'un span **non vide** ; les fragments vides
  qui partagent l'id sont retirés ;
- la branche multi-nœuds ne renvoie plus `true` inconditionnellement (elle
  renvoyait vrai même si 100 % des `surroundContents` échouaient, donc
  `applyHighlights` ne tentait jamais le repli `wrapOnce`) ;
- le toast de succès vérifie désormais qu'un span existe avant de dire
  « cliquez le passage surligné ». Un toast ne doit jamais mentir.

**Méthode qui a payé** : j'ai d'abord cru au `stopPropagation()` du module v86
(mot), puis au `return true` inconditionnel. Les deux hypothèses étaient
**fausses** — le test de causalité les a écartées. Ce qui a tranché : monter un
banc où l'on pose l'annotation puis on **compte les spans vides** dans le DOM.
Conclusion à retenir : sur ce projet, une hypothèse lue dans le code ne vaut
rien tant qu'un banc ne l'a pas départagée d'une autre.

## « Pourquoi je n'ai pas de mise à jour sur mon dépôt » — le filtre `paths`

Fatih a signalé l'absence de mise à jour. Le code **était** poussé (`23e2c13`,

### Cause : le workflow filtre sur `paths:`, et mon commit n'y touchait rien

**Après un push, vérifier qu'un run CI existe — pas seulement que le push est
passé.** `git ls-remote` prouve l'arrivée du commit, pas le déclenchement du

`.workbuddy-ai/`, soit il n'y a rien à livrer, soit il faut ajouter le fichier
concerné au filtre.

**Le sandbox bloque le téléchargement des assets de Release** (`curl` sur
`releases/download/...` rend un fichier vide) : on ne peut pas vérifier le
contenu binaire publié depuis ici. Passer par l'API Actions (jobs + étapes) pour
prouver que la CI est allée au bout.

### Extraction de la vidéo

ffmpeg disponible via WinGet (`.../Gyan.FFmpeg_Microsoft.Winget.Source_.../bin`).
- `ffprobe` **échoue sur un chemin avec espaces** → copier vers un chemin simple.
- `-pix_fmt yuvj420p -strict unofficial` obligatoire, sinon l'encodeur mjpeg
  refuse le flux (`Non full-range YUV is non-standard`).
- Les images (1/4 s) montrent la séquence : panneau ouvert sur le lien, puis
  curseur qui descend, puis panneau disparu. C'est ce qui a orienté la mesure.

### Cause, mesurée au traceur CDP

En quittant le lien vers la ligne de mots, le navigateur émet **UN SEUL
`mouseout`** sur le lien, avec `relatedTarget` = **le fond de page**, pas le
panneau :

```
[0] de=LIEN cible=quran-ref -> relatedTarget=message message-assistant
    rt dans panneau=false  rt dans fiche=false  panneau encore visible=true
```

`dansPanneau()` renvoie donc `false` et `hideTip()` s'exécute pendant que la
souris est encore en chemin. **La géométrie rend ça inévitable** : le panneau
est posé AU-DESSUS du lien (y=472 contre y=659), donc rejoindre un mot oblige à
sortir du lien par un bord où le panneau n'est pas encore. **Juger sur
`relatedTarget`, c'est juger un chemin que le curseur n'a pas fini de
parcourir.**

### Correctif

On juge la **destination**, pas le chemin : la fermeture est **armée** au
`mouseout` (160 ms) et **annulée** par tout `mouseover` visant le panneau, un
mot ou une fiche. Appliqué à **Bible, Coran, Tafsir**. `#verse-mini-tip` avait
déjà cette forme (250 ms + test `:hover`) et `#v37-tip` se déclenche sur le mot
lui-même : ni l'un ni l'autre n'avait besoin d'être touché.

Mesure avant/après, même script, même trajet :

| | avant | après |
|---|---|---|
| pas 6/12 | `visible:false` | sous `#quran-verse-tip` |
| pas 12/12 | `visible:false` | sous `qw qw-actif` |
| état final | **PANNEAU FERMÉ** | **PANNEAU OUVERT** |

`verif_biblique.js` : **10/10** — le panneau survit à la descente, la fiche
s'ouvre, elle est au-dessus (`9500 > 9000`), la translittération est réellement
rendue (`wayoʾmer`, lemme `אָמַר · aw-mar'`, `Strong 559`), c'est bien elle qui

désinstalle pas en réaffectant une valeur : il faut `delete t.style.display`.

## Le piège des secrets — même cause, enjeu tout autre

En corrigeant la question des APK, je me suis demandé ce que `git add -A` prendrait
d'autre. Réponse : **`git check-ignore` ne protégeait ni
`THEOLOGICUS_signing.pfx`, ni `signing_key.pem`, ni `signing_cert.pem`, ni un
fichier nommé « mistral api key.txt »** — tous à la racine du dépôt.

C'est **le même piège que les APK** (hors git par accident de `git add`, pas par
règle), mais l'enjeu n'est pas le poids : `THEOLOGICUS_signing.pfx` est la clé qui
donne son identité à chaque APK publié, et son mot de passe est rangé à côté. Si
elle entre dans l'historique, **elle y reste** : n'importe qui peut alors publier
une mise à jour que nos utilisateurs installeraient. Un `*.apk` mal committé se
retire ; une clé de signature divulguée ne se retire pas.

Motifs ajoutés : `*.pfx`, `*.p12`, `*.jks`, `*.keystore`, `*.pem`, `*.key`,
`*api key*.txt`, `*mistral*key*`, `*secret*`, `*credential*`.

**Non-régression vérifiée** : `git ls-files | git check-ignore --stdin` rend
**vide** — aucun fichier déjà suivi ne tombe sous les nouveaux motifs.
`build_installer.bat` ne référence le `.pfx` que par **nom local** ; la CI signe
depuis les secrets du dépôt, donc rien de légitime ne casse.

### La leçon, une seule fois écrite

**Ce qui doit rester hors du dépôt s'écrit dans `.gitignore`. Cela ne se
retient pas.** Deux fois le même jour j'ai cru à une règle qui n'existait pas —
les APK d'abord, les secrets ensuite. Le contrôle est mécanique :
`git check-ignore -v` doit **nommer** le motif, et `git add -An` doit **refuser**.

### 2. Le burger ne cachait pas le rail sur Windows

Une **accolade fermante en trop** dans `<style id="v6-ui-css">` : elle fermait
`@media screen and (max-width:640px)` avant l'heure, laissant une accolade
orpheline. **Erreur de syntaxe CSS → le parseur abandonne tout ce qui suit.**
Le `@media (min-width:901px)`, seul porteur du repli (`margin-left:-268px`),
n'était donc **jamais enregistré**. Le burger basculait la classe
`sidebar-open` ; **rien n'écoutait**. Sous 1024 px ça marchait parce qu'une
*autre* feuille prend le relais — d'où un défaut invisible en mobile.

Preuve : le `textContent` du `<style>` contenait bien `min-width:901px` et
`-268px`, mais le CSSOM ne listait que `(max-width:900px)` et
`(max-width:640px)`. **Le texte dit une chose, le CSSOM une autre → la feuille
est tronquée.** Après correction, `(min-width:901px) [2 regles]` apparaît et à
1200 px le rail passe visible→caché, `margin-left` 0→-268px. Les quatre
largeurs testées basculent.
