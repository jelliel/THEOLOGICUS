## Bug mobile corrigé (v38, versionCode 2)
**Symptôme :** sur Android, après interaction avec le clavier logiciel,
l'app est dessinée dans une bande au milieu de l'écran (zones noires du
fond `body` au-dessus et en-dessous).

**Cause :** bug connu Android WebView : le **layout viewport** (utilisé
par `100vh`) ne se restaure pas correctement après l'apparition/disparition
du clavier. Le shell (`height: 100vh` sur mobile) se base alors sur un
viewport trop petit.

**Correctif :** mini-script inline (après le shim v34, Capacitor-only)
qui pose `--app-h = window.innerHeight` sur `<html>` (visual viewport qui
se restaure), avec écouteurs `resize`/`orientationchange`. Le CSS
utilise `var(--app-h, 100vh)` pour `body:has(.tpai-shell) { min-height }`
et `.tpai-shell { height }` (mobile). Fallback 100vh → desktop intact.

**Reproduction qui n'a PAS montré le bug :** headless Chrome avec
émulation mobile 360×780 → shell.top=0, shell.height=viewport. Donc le
bug est strictement Android WebView (pas un bug CSS générique).

## Bugs mobiles corrigés (v40 — versionCode 14)

### 1. Le rail latéral ne s'ouvrait jamais au doigt — LA cause
`iPadTouchFix()` (~ligne 15413) : un `touchend` sur n'importe quel bouton
re-déclenche `el.click()` 12 ms plus tard **sans vérifier** si le
navigateur a déjà émis le clic. Sur WebView Android il l'émet, donc tout
bouton était actionné **deux fois** → `classList.toggle('sidebar-open')`
ouvrait puis refermait → « je clique dessus, ça n'ouvre pas ».
Preuve CDP : 2 événements `click`, le 2ᵉ avec `isTrusted:false`,
`detail:0`, ciblé sur le `BUTTON` (signature de `el.click()`).
**Correctif :** drapeau `nativeClickWorks` posé par un écouteur `click`
en capture (`isTrusted` et < 500 ms après un `touchend`). Le clic natif
arrive avant le `setTimeout(12)` → le filet est neutralisé dès le premier
tap, et reste actif si le navigateur n'émet rien (bug iOS d'origine).
**Ce doublon touchait TOUS les boutons mobiles**, pas seulement le burger.
À retenir : un bug « ça ne réagit pas au doigt » = chercher un double
déclenchement avant de chercher un problème de CSS.

### 2. Le correctif v38 était inopérant
`.tpai-shell { height:100vh !important }` (CSS v6, ~ligne 20369) écrasait
`height: var(--app-h, 100vh)` qui n'avait pas `!important`.
→ passé en `height:var(--app-h, 100vh) !important`.
Piège : vérifier les surcharges `!important` concurrentes, pas seulement l'ordre.

### 3. Zone sûre + cible tactile
- `viewport-fit=cover` ajouté au meta viewport (il manquait → les
  `env(safe-area-inset-*)` valaient 0 partout).
- `.tpai-shell { padding-top: env(safe-area-inset-top, 0px) }`.
- rail : `top: calc(62px + env(safe-area-inset-top, 0px))` — le conteneur
  d'un absolu est la **padding-box**, donc un `padding-top` ne le décale pas.
- `.v6-iconbtn` (burger) : 32 px → 44 px (oublié par la liste v35).
- erreur de syntaxe `background: ...0.97));` dans la règle du rail.

### Auto-incrément de version
`android/app/build.gradle` : `versionCode` = `git rev-list --count HEAD`
(surcharge par `APK_VERSION_CODE` / `APK_VERSION_NAME` si fournis).
CI : `fetch-depth: 0` + étape « Compute version from commit count » ;
`github.run_number` remplacé par `env.VERSION_CODE` / `env.VERSION_NAME`
dans les deux jobs (les deux publications de release doivent avoir le
même `tag_name`, sinon elles partent sur des tags différents).

## Sélection de texte au doigt (v41 — versionCode 15)

Deux causes distinctes au même symptôme « je sélectionne, je n'obtiens pas
Add to chat » :

1. **La bulle de sélection avait 12 actions** (Note, Google, Wikipedia,
   Bible, Bible Hub, Surligner, Partager, Encadrer, Lire, Question,
   Traduire). Au doigt elles sont trop serrées et un double tap ouvrait
   « Encadrer » au lieu d'ajouter au chat.
   → `showBubble()` masque tout sauf `.atc-main:not(.atc-note-btn)` quand
   `__THEO_TOUCH_UI()` est vrai. Le bureau garde les 12.

2. **Un tap émet `mouseover`** sur mobile. Le gestionnaire
   `mouseover → showTipFor()` (survol d'un passage annoté) se déclenchait
   donc à chaque toucher, ouvrant l'infobulle d'annotation au lieu de
   laisser la sélection se faire.
   → garde `if (touch) return;` au début du handler. Le survol n'a aucun
   sens au doigt.

`window.__THEO_TOUCH_UI()` = Capacitor natif **ou** `(pointer: coarse)`.
Globale volontairement : les deux points d'usage ne partagent pas la
même portée.

**Piège de test :** sélectionner un nœud de texte de l'app ne tient pas —
l'interface se re-rend et la sélection est vidée (`toString()` vide).
Injecter son propre `<div>` stable. Et `showTipFor` exige une annotation
réelle dans `state.messages[].annotations`, sinon il sort sans rien créer.

**Piège d'outil :** `tools/prepare_mobile.py` fait `shutil.rmtree(mobile/www)`
(330 fichiers) → déclenche le garde anti-suppression groupée. Contourner en
ne réécrivant que `mobile/www/index.html` avec la même transformation
(viewport + tampon `__THEO_VERSION__`).

À noter : `viewport-fit=cover` n'est **pas** dans le HTML source, il est
injecté par `prepare_mobile.py` au moment du build mobile.

## Annulation partielle de v41 → v42 (versionCode 16)

L'utilisateur voulait **récupérer toutes les actions** de la bulle (v41 les
avait réduites à « Add to chat »). Leçon : raboter des fonctions n'était pas
la bonne réponse, le vrai problème était géométrique.
- `showBubble()` : branche tactile supprimée, retour à la logique d'origine.
- CSS : `#atc-bubble { flex-wrap: wrap; max-width: calc(100vw - 16px) }`,
  cibles 44 px sur `.atc-main/.atc-act/.atc-share`, séparateurs masqués.
  Vérifié 412 px : 12 actions, aucune < 44 px, bulle 396 px sur 2 lignes.
- **Double-tap → encadrement** : deux `touchend` à < 350 ms et < 40 px
  ouvrent `openInsertMenuAt()`. Fait à la main car `dblclick` est déjà pris
  par le renommage de conversation et n'est pas fiable sur WebView.
  Tactile uniquement. La bulle est masquée pour éviter le conflit.
- La garde `mouseover` (infobulle d'annotation) est **conservée** : un tap
  émet mouseover, sans elle chaque toucher bloquait la sélection.

## v43 — deux pannes majeures de l'APK (versionCode 17)

### 1. Tous les appels IA échouaient sur le téléphone
`apiEndpoint()` réécrit chaque URL de fournisseur en `/proxy/<url>`, servi
par `proxy_server.py` (lancé par `app.py`, l'app pywebview). **Ce serveur
n'existe pas sur le téléphone** → requête vers
`https://localhost/proxy/...` → 404 → « Erreur API ». Ce n'était pas le
bouton ❓ : **le chat entier était mort sur l'APK**.
Vérifié que le proxy ne fait que relayer les en-têtes (Authorization,
x-api-key…) et le corps — il n'injecte aucune clé → l'appel direct est
équivalent. Désormais : natif → URL directe.
Anthropic exige `anthropic-dangerous-direct-browser-access: true` depuis un
navigateur (ajouté via `anthropicHeaders()`). CORS vérifié en préflight :
Mistral `access-control-allow-origin: *`, OpenAI renvoie `https://localhost`.

### 2. Bouton « Plus » hors écran en portrait
Mesuré : bord droit à **414 puis 437 px** pour un écran de **412**. Or v6
**déplace** tous les boutons de modals dans ce menu (`moveTo()` fait un
`appendChild`) → ils étaient tous inatteignables.
Correctif : `#v6-topbar` réserve 104 px à droite et le groupe
recherche+Plus (`#v6-right-grp`, nouvel id) est ancré en absolu → toujours
atteignable quel que soit le contenu. Résultat mesuré : 362–406 px.
Le menu reçoit aussi `max-height: calc(100vh - 70px)` + `overflow-y: auto`
(sinon les dernières entrées sont coupées sans défilement).
**Tenter d'abord « laisser le contenu se comprimer » a empiré** (414 → 437) :
avec `flex: 0 0 auto` le groupe glisse davantage. L'ancrage absolu est la
seule solution robuste ici.

### Leçon générale
Mesurer les `getBoundingClientRect()` en émulation téléphone avant de
toucher du CSS de mise en page : l'hypothèse « ça déborde » a été confirmée
en une mesure, alors que deux raisonnements a priori s'étaient trompés.
