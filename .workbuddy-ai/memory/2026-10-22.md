## v633 — POURQUOI LE CORRECTIF v632 N'A RIEN CHANGÉ (mesuré sur le vrai store)
Le défaut persistait : « refais une autre analyse ». Analyse faite sur la DATA
RÉELLE (`%LOCALAPPDATA%/THEOLOGICUS/theologicus_store.json`, 27 Mo, clés
`chat::*` = JSON encodé sous `keys[k]["v"]`) et sur la capture du 22/10 14:15.

🔴 **Cause n°1 — 319 des 320 figures n'ont AUCUNE ancre.**
`insertFigureAt` ne crée l'ancre que si `target.selRect && target.range`
(2 conditions). Toute insertion dont la sélection est perdue au moment du clic
(cas courant : menu d'insertion, re-rendu, clic programmé, encadré posé à la
main) produit `ancre: null`. `_ancPlace` sort immédiatement si `!f.ancre` :
**le re-ancrage v632 ne s'applique donc jamais** sur ces figures. Le travail de
la session précédente portait sur les 0,3 % (1 figure) ayant survécu.
→ invariant faux : on a fait « suivre le texte » une fonction que 99,7 % des
figures ne traversent jamais.

🔴 **Cause n°2 — l'ancre de cette unique figure est CORROMPUE.**
`fg-1792669136788` : `ancre.start=9789, end=9854`, `texte="« Kyrios est le
Seigneur des pauvres (Lc 4,18), pas des oppresseurs. »"`.
- `message[9789:9854]` = `'rain**.\n 2. **Étudier *Kyrios* dans le NT** →…'`
- le vrai texte est à **12406**, soit **2617 caractères d'écart**.
- ❗ le texte d'ancre n'existe **NULLE PART** dans le message (`find` = -1).
Cause : `computeOffsetInBoxFiltre` renvoie `start=0` / `end=total` quand la
sélection commence ou finit dans un nœud EXCLU (v632e) — l'ancre couvre alors
tout le message ; et deux espaces d'offsets (canonique ≠ `content` brut) sont
mélangés.

🔴 **Cause n°3 — la forme dominante est `Carré` (297/320)**, et un cadre
« hauteur 34 » est le minimum CSS (34 px). Les cadres vus « en barres fines »
sont des cadres réalisés avec une sélection sur UNE LIGNE (hauteur de ligne
= 17 px + 16 = 33 → 44/34) : la géométrie est « fidèle » à la sélection, mais
elle ne contient pas la phrase entière aux yeux de l'utilisateur.

→ Conclusion : le bon modèle n'est pas « offset + texte optionnel ». Il faut :
(a) ancrer l'ancre sur le TEXTE TOUJOURS, même sans `range` (repli sur le mot
cliqué / la sélection courante) ; (b) relire l'ancre par TEXTE EXACT dans le
contenu canonique, l'offset n'étant qu'un départage ; (c) ne jamais produire
0/total ; (d) réparer au chargement les figures existantes sans ancre en
retrouvant leur texte par recouvrement géométrique.

## v635 → v646 — « pire et pire » : la dérive CUMULATIVE des encadrés

Deuxième passe, sur le même symptôme. v632/v633 avaient réparé l'ancrage ; la
plainte persistait : *« les encadrements ne sont pas respectés en position, à
chaque démarrage ça change de place, et c'est pire et pire »*.

### La mesure qui tranche

Sur le **build déjà livré** (b9e17cb), banc de données réelles :

| | build livré | après v635-v646 |
|---|---|---|
| figures ancrées | 27/27 | 27/27 |
| figures **couvrant** leur ancre | **1/27** | **27/27** |

Donc v632/v633 posaient bien une ancre, mais **26 cadres sur 27 ne
couvraient plus le texte qu'ils désignaient**. C'est le bug que
l'utilisateur voyait, chiffré.

### Les quatre causes (toutes mesurées, aucune supposée)

1. **La largeur héritée** — `_ancFit` faisait
   `Math.max(f.w, min(rr.w + 16, clientWidth))`. Pour une ancre
   **multi-lignes**, `rr.w` = largeur du BLOC = ~971 (conteneur 974) : un
   cadre de 420 px devenait 974. Et comme `f.w` élargi redonnait le `_w0` du
   démarrage suivant, **la largeur montait à chaque redémarrage** → 447→1612
   px mesurés sur 12 cadres. Correctif : `ow`/`oh` sont ceux du **cadre**, avec
   un plancher borné à la largeur de la **PREMIÈRE LIGNE** (`Range` sur un
   seul rang, `getClientRects()[0]`), plafond ×1,6. Résultat : 200→237 px pour
   un texte de 221 (au lieu de 974).
2. **Le bornage sur la hauteur VISIBLE** — `by` était borné par
   `box.clientHeight` (727 au 1ᵉʳ passage, 849 ensuite) au lieu de la hauteur
   de contenu. Un même cadre était borné différemment selon l'instant.
   Correctif : `_ancHauteurZone()` = `scrollHeight`, dans les DEUX sites.
3. **Le moment du placement** — le contenu du message grandit **après** la
   première passe (fiches, puces de sources). Rien ne rejouait le placement :
   le cadre restait à 240 px (provisoire) au lieu de 301 (final). Correctif :
   `_atcSettle` branché sur `_atcScheduleApply` (1 passe + reprises 120/400/900
   ms, annulées à chaque appel).
4. **Le geste annulé** — une passe de stabilisation replaçait le cadre sur son
   ancre après un glissement manuel. Correctif : `_atcSettle` s'abstient si
   `__atcFigEditing` ou si `__atcGeste > _seq0`.

### Les pièges rencontrés (à ne pas refaire)

- 🔴 **`once()` qui ne réassigne pas** : le script annonçait « OK » avec
  **octets identiques avant/après** (7 949 128 dans les deux cas). Un patch
  doit **prouver** l'effet : post-condition `if out == src: REFUS`.
- 🔴 **`typeof atcPersist === 'function'`** → `"undefined"` (portée de bloc) ;
  la garde sautait l'appel **en silence**. Les globaux PROUVÉS sont
  `saveChat`, `flushChatNow`, `markChatDirty`.
- 🔴 **`saveChat` écrit dans IndexedDB**, pas dans `localStorage`. Lire
  `localStorage` pour juger la persistance a fait croire pendant 5 versions
  que « le store n'apprend rien » alors qu'IDB était déjà juste. `localStorage`
  n'est que le filet (`flushChatNow`).
- 🔴 **Ne pas référencer `m` dans `_ancPlace`** (v639) : `m` est la variable de
  boucle d'`applyShapes`. Le `ReferenceError` était avalé par le `try/catch` →
  `ancre: null`, réparation morte **sans aucune erreur visible**.
- 🔴 **Trois espaces de coordonnées** dans un banc : `_ancRect` renvoie du
  conteneur **scroll inclus** ; y rajouter `br.top` sans soustraire
  `scrollTop` donne `dtey = 952` (= le scroll) sur un cadre correct.
- 🔴 **Un rapport impossible est un défaut de mesure** : `27 ancrées / 26 sur
  texte` ne peut pas exister. Chercher l'erreur dans le banc avant le produit.
- 🔴 **Un cadre hors viewport ne recouvre aucun texte mesurable** : compter
  « sur texte » avant de l'avoir amené à l'écran fausse le dénominateur.

Chaîne : chaque `fb.style.left = …` mute le DOM → MutationObserver de `cc` →
`_atcScheduleApply` → `_atcSettle` → `applyShapes` → `_ancPlace` **recalcule**
la position depuis l'ancre et écrase. Le garde `__atcGeste > _seq0` ne
protégeait de rien : `_seq0` est pris À L'APPEL de `_atcSettle`, donc un geste
ANTÉRIEUR à l'appel ne bloque jamais. Et le glissement n'appelait jamais
`_figEditing()` (seules les barres d'outils le font).

### Cause 2 — le déplacement n'était pas REPRODUCTIBLE

Même après un `persistFig` correct, la branche `cx` de `_ancPlace` **centre** la
boîte : `nx = rr.x + (rr.w - nw)/2 + dx`. Une boîte plus large que son ancre
donne un terme négatif, puis le borne-bas à 0 : `dx=30` enregistré, cadre rendu
à `left=0px`.

### Correctif (3 invariants, `_v647/patch_v647.py`)

1. `_ancPlace` commence par `if (figEl.__atcGeste) return;` — un cadre **saisi**
   n'est plus replacé.
2. Le `mousedown` pose `fb.__atcGeste = true` (et `window.__atcGeste`), le
   `mouseup` le lève **avant** `persistFig`.
3. Un DÉPLACEMENT mémorise l'écart **au coin de l'ancre** (`ancre.ox/oy`,
   référence fixe : `rr.x + ox` restitue au pixel) au lieu d'accumuler
   `dx/dy` sur un centrage ; `cx` est alors supprimé, `ow/oh` restent
   immuables → l'idempotence v634 est conservée. Repli `dx/dy` si l'ancre n'a
   pas de texte résoluble.
